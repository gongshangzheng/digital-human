## Context

Proposal 已说明问题：同一条线的事实散在 `工程设计.md` 的 5 处，而真正的源设计文档在 CyberVerse 仓库（`management/docs/silent-avatar-feed-gate.md`，本仓库只在 `knowledge/README.md` 第 52 行登记文件名）。

设计阶段要固定的额外约束有四条：

1. **不能靠搬迁解决重复**：5 处里有 4 处的内容属于各自节的机制（编码进程、段与发布节奏、音频链路），搬走会让那些节失去依据。所以本节的原则是「**事实只在状态机节出现一次；机制细节留在原节并被引用**」。
2. **本节要写的是状态机，不是流水账**：现在的 `### 打断与收声的状态机` 只有"期望行为 + 两缺陷 + 四组改动名目 + 四版失败"，缺状态枚举、事件、迁移条件与兜底。本节要把这些补齐成可读的结构。
3. **参数是快照**：外部文档的参数表是 2026-07-31 的取值，必须标注日期并说明"以源码常量为准"。
4. **与《数字人领域问题》新章联动**：并行 change `docs-dh-field-model-boundary` 新增的 `## 八、工程问题模型化` 里，段 3 判定清单的前两条（回合边界、聆听态内容）要引用本节作为"工程侧现在怎么做"的事实底稿。两节的交叉引用需在实施时对齐。

## Goals / Non-Goals

**Goals：**

- 在 `工程设计.md` 新增 `## 状态机设计`，把状态枚举、事件、迁移、两级水位、转场策略、音频侧连续性要求、失败判据、三次误诊、诊断表与未决收在一处。
- 让 `工程设计.md` 自洽：读者在这一节能读到**待机 ↔ 说话 ↔ 打断**的完整转换，不需要跳去另一个仓库才能理解。
- 收编外部源文档的**结论与判据**（水位取值与由来、视频永不剪、三次误诊、日志诊断表），并给出外部源指针。
- 修好两处断链：外部源文档、以及《数字人加速》的 `### 首帧与开口`（反向切换）。

**Non-Goals：**

- 不搬编码进程、段与发布节奏、音频链路三处的机制细节（保留原位，本节引用）。
- 不复制 CyberVerse 文档全文与其源码行号清单；不复制代码实现。
- 不写《数字人领域问题》的判定与结论（那是新章的职责，本节只给事实）。
- 不改 frontmatter 与 `order`；不改其他节的事实与数字。

## 1. 落点、标题与篇幅

- **落点**：`## 音频链路设计` 之后、`## 会话与资源生命周期设计` 之前。
  - 理由：本节依赖两侧机制先被交代——发布侧（段长按状态区分、打断时编码器重生）与音频侧（静音流连续性、带下限归一化）；同时把它与 `## 稳定性设计`（断连、雪花、背压）分开，因为那一节是**异常路径**，本节是**正常态之间的转换**。
  - 备选：把 `### 打断与收声的状态机` 就地提升为 `##`（否决：稳定性设计还含断连/雪花/背压，把常态转换塞在"稳定性"里会让两类问题混淆）。
- **标题（默认）**：`## 状态机设计`。备选：`## 待机与说话的转场设计`。
- **篇幅**：8 个小节，正文（不含表与 Mermaid）目标 ≤ 2500 字符；表 3 张（状态与事件、外部参数快照、日志诊断表）、Mermaid 2 张（状态图、转场时序）。
- **元数据**：不改 frontmatter；`order` 与章节总数以外的排序不变。

## 2. 章内结构（八小节）

| # | 小节 | 论点/结论 | 素材来源 | 处理方式 |
|---|---|---|---|---|
| 0 | 章首一句 | 事实以 CyberVerse 源文档为准，**参数快照 2026-07-31** | 外部源 | 新增 |
| 1 | `### 状态与事件` | 状态枚举（**待机 / 说话 / 爬坡 / 预缓冲 / 收尾聆听**）+ 事件（用户语音到达、TTS 供料结束、用户打断、喂料饥饿 2s、会话终止）+ 迁移图；段长按状态区分（数值见《传输与发布设计》） | `### 段与发布节奏` + 外部源状态语义 | 新增（状态枚举来自既有"段长按状态区分"一行，展开成表） |
| 2 | `### 喂料阀与两级水位` | `lead = 已喂入音频样本 − 已回收视频对应的音频样本`；**待机要浅、说话可深**（待机呼吸是纯延迟：说话到来时它必须先渲染播完）；参数快照表；**换轮延迟 ≈ LLM+TTS + 待机水位 + 下游库存**，所以待机水位是主项 | 外部源 §一/§二 + `### 背压与限流（进行中）` | 收编（事实为主） |
| 3 | `### 转场策略：视频永不剪` | FLUSH 只发生在 seek / 打断；**待机→说话不是不连续点**（呼吸帧就是此刻该播的画面）；打断走 `AdvancePlaybackEpoch` + `Invalidate` 出新 IDR；反面做法（剪视频换说话延迟）的代价：一次转场丢 600–1200ms 已生成呼吸动作 → 画面跳一下 | 外部源 §三.2 + §四 | 收编 |
| 4 | `### 音频侧的连续性要求` | 静音流必须跨块连续（逐块重置 → 10Hz 锯齿，块内标准差 0.00118 vs 一次性生成 0.0133）；静默期归一化必须带下限（否则呼吸底噪 RMS≈0.02 被放大到单位方差 → 头部逐渐放大的漂移） | `音频链路设计` 两条 | **引用不搬**（各留一句"与状态机的关系"） |
| 5 | `### 收尾：为什么"立即止声"被推翻` | 期望行为（打断 → 尾音 1.5s 内自然收住 → 闭嘴聆听 → 新话开始、全程无冻帧）；两个已定位缺陷（语音绕过门控导致模型内积压、epoch 硬切把画面冻在末帧）；四组改动（门控时长 / 软切护栏 / 放行预缓冲段 / 缓冲调参）；**4 版被推翻**（画面冻结 / 长度难调 / 尾音被一起丢弃）；判据是**人眼与听感** | 现 `### 打断与收声的状态机` | **整体移入**，原位留一行指针 |
| 6 | `### 三次误诊与纠正` | ① 误诊"需要未来音频"（`overlap_v2` 数的是**历史**帧；`valid_clip_len = 80−70 = 10` 帧 = 0.4s；online 预填 70 帧静音作历史 → **零未来音频依赖**；真正下限是管线在途占用）；② 用"剪视频"换说话延迟（已改掉）；③ 编码后丢段（NVENC 持久进程是**一条连续 GOP**，丢段不触发 IDR → 雪花屏） | 外部源 §三 | 收编 |
| 7 | `### 诊断表（按日志定位）` | 7 条日志与异常判据（`lead resync` 应为 0；`speech feed start ... lead_ms` 恒等于待机水位属正常；`stalls` 增加即回归；`h264 stream respawn` 应仅出现在打断；`publish hole` >60ms 告警；`idle superseded ... dropped_idle_ms` **再次出现说明"永不剪"被回退**） | 外部源 §五 | 收编（保留日志名，因为它是判据的唯一锚点） |
| 8 | `### 未决与后续` | 限流阀重构（两级水位 + FLUSH + 单一 work-ahead 上限）与 `lead` 记账变负的缺陷；`cv:flush` 抽换未消费音频（水位降到 2.0s 后收益变小，按实测决定）；待机水位继续下探（2.0 → 1.4s，判据仍是 `lead resync` 归零）；`livekit/bot.go` 仍保留 supersede 丢弃（当前 `streaming mode: direct` 不启用） | `### 背压与限流（进行中）` + 外部源 §六 | 收编（与背压节分工：本节写状态机侧的结论，背压节保留"自锁"的成因与判据） |

**Mermaid 1 · 状态图**（`stateDiagram-v2`）：待机 →（用户语音到达）→ 预缓冲 → 说话 →（TTS 结束）→ 收尾聆听 → 待机；任意状态 →（用户打断）→ 收尾聆听（渐弱尾 + 新 IDR）→ 待机；待机/说话 →（喂料饥饿 2s）→ 强制对齐记账（`resyncLead`）。

**Mermaid 2 · 转场时序**（`flowchart`，改自外部源 §四）：待机喂呼吸至 `lead = 2.0s` → 说话到达停喂待机 → 说话音频排在已喂待机之后 → 模型按 0.4s 步长出画 → **待机视频照常播完、不剪** → 说话视频接上；打断分支：清 `speechCh` + 渐弱尾 + `AdvancePlaybackEpoch` → 丢在途视频 + 新 IDR。

## 4. 收编边界（与外部仓库的分工）

- **收**：状态与事件语义、两级水位的取值与由来、转场策略与其反面教训、三次误诊的结论、日志诊断表、未决项。
- **不收**：代码实现与文件行号清单、Go/Python 侧的调用细节、外部文档的全文结构。
- **保留源码常量名**（如 `silentAvatarIdleLeadFloor`）：它们是"判据能落到代码"的唯一锚点；若你希望更保守，可只保留数值并去掉标识符（待决项 2）。
- **参数快照标注**：章首一句 + 参数表标题注明"2026-07-31 快照，以源码常量为准"。

## 5. 与其他文档的接口

- 新节是《数字人领域问题》`## 八、工程问题模型化` 的**事实底稿**：该章段 3 判定清单的前两条（打断与回合边界、聆听态内容）以本节的"工程侧现状"列为输入；实施时必须对齐两处的措辞与数字。
- 与 `## 稳定性设计` 的分工：本节管**正常态之间怎么切**，稳定性设计管**异常路径怎么兜**（断连恢复、雪花帧、背压自锁）。
- 与 `## 传输与发布设计` 的分工：本节管**状态与转场策略**，那一节管**编码进程与发布节奏的机制**。

## Risks / Trade-offs

- [搬迁导致原节失去依据] → 只有 `### 打断与收声的状态机` 整体移动（其余为引用），并在原位留指针；实施后通读原节确认无悬空引用。
- [本节变成外部文档的副本] → 收编边界见 §4；代码级细节一律外链；不抄文件行号。
- [与《数字人领域问题》新章的措辞/数字不一致] → 实施顺序上先做本节（事实底稿），再做那段判定；或同批实施并交叉核对。
- [参数快照过期误导] → 章首与表标题标注日期，并写明判据以源码为准。
- [节过长] → 表格化 3 处、Mermaid 2 张承担结构与时序；正文目标 ≤ 2500 字符。
- [新节与七章编号冲突] → 本节是《工程设计》内部的新 `##`，不涉及《数字人领域问题》的章号，无冲突。
