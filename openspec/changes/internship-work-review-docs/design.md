# Design: internship-work-review-docs

## Context

- 目标读者：**自己**。用途：① 工作汇报底稿；② 为后续继续推进数字人方向的工作提供素材；③ 循实习经验提炼可发表文章的选题依据。写作取向：事实与数字优先，每个结论给证据锚（代码路径/commit/指标表），区分"已验证/待验证/已被否证"。
- 素材四源：CyberVerse（`~/code/CyberVerse` @ `4968280`）、InternWiki（已复制至 `management/docs/knowledge/`）、博客精选（已复制）、InternWiki 项目树（`projects/digital-human/tasks.json`）。
- 放置规则（用户明确要求）：子文件夹夹内平铺、禁止再嵌套。两个子文件夹：`实习复盘/`（8 篇）、`论文笔记/`（统一笔记库）。
- 内容文档（非索引/汇总类）统一写作骨架，**不是单纯写"我们改了什么"**：
  1. `为什么重要` — 这部分在数字人系统里为什么关键、不做会怎样
  2. `现行做法` — 该方向的信息总结：主流算法一般怎么做、有哪些流派与代表工作
  3. `我们的工作` — 我们做了哪些实验/实现/结论（含否证）
  4. `可能的改进方向` — 基于以上，可尝试的改进方向（开放问题）

## Goals / Non-Goals

**Goals:**
- 9 篇复盘 + 论文笔记，每篇内容文档按统一骨架成文（重要→现行→我们的→改进方向）
- 支撑工作汇报：量化成果总表可直取直用
- 支撑后续推进：遗留问题、未采纳方案、下一步补实验清单清晰可执行
- 产出《发文方向》：每条候选选题一张"证据资产负债表"

**Non-Goals:**
- 不做团队交接文档（读者是自己）
- 不复制/搬运 knowledge/ 已有内容，只做第一方复盘并引用
- 不虚构数字，查不到的写"待补"

  - **3D GS 路线**（UIKA、GAGAvatar、LHM 等）
- `## 评价体系`：先定义**评价维度**（从哪个层面评）与**评价指标**（用哪个数字量评）两个术语，再分三节——三个评价维度、五个评价指标族（sync_c/sync_d、csim/psnr/ssim/lpips/topiq_fr、RTF/延迟 等各回答什么问题）、两者的对应关系表（并指出「表现范围」缺通用量化指标）；**动作与身份两个因素分别对应到指标族**（动作→唇同步/动作自然度；身份→CSIM/画质）

    - `### 原生怎么保身份，又为什么会漂`：原生机制（参考图初始化编码一次得 512 维身份项，全程固定；重建 = 身份项 + 运动项；`r = Bα` 实为 20 维子空间）→ 原生无任何推理期锚定 → 漂移三层原因（解耦只是近似 / 因果滚动累积误差 / 长时无回看闭环）；点明"模长没涨、方向在转"的诊断要点
    - `### 漂移出在哪（模长还是方向）`：**先交代实验载体**（Avatar Forcing 流式路径、被测量的 motion latent、身份侧固定为 appearance code、c1 单身份 300 秒，接入细节链 `docs-note-avatar-forcing`）→ 模长实验被否证 → 夹角实验仅在单身份上得到支持
    - `### 三种治理手段与结果`：A1 锚点引导 GO / 参考条件化 v1 失败与 v2 归档失败 / Learned Anchor Force 终止
    - `### 锚帧库与参考图怎么选`：锚帧库/身份特征字典怎么建（帧数与角距分布）、参考帧策略三档（fixed / rolling / reset-N）与训推一致性、换身份成本曲线（我方实测数）；"注入时机与开销"归 `## 身份注入与保持`
    - `### CSIM 当损失函数（已放弃）`：把**身份相似度**（ArcFace 系 embedding 的余弦，即 CSIM 的定义；业界叫 ID loss / Face Sim loss）当训练损失做单身份微调；**注意与 ArcFace 论文的 AAM 分类损失不是一回事**（后者需要多身份标签）；**放弃原因（已确认）：身份相似度确实改善，但它管不住脸部尺度漂移（忽大忽小），而尺度漂移才是流式体验上最刺眼的问题**——身份相似度是标量，漂移有模长/方向/尺度多个维度，不重合；尺度漂移后来在流式侧按归一化处理（细节归《工程设计》的音频链路设计）。指标记录三处均无 → 不编数字
- `## 可能的改进方向`：多身份夹角验证、治理消融、身份资产协议标准化
- `## 汇报要点`：一页可直取的结论（含三个结论：模长否证 / 方向仅单身份支持 / A1 有效；两个反例：参考条件化 v2 回退、LAF 头抖；一个放弃：CSIM 当损失管不住尺度漂移；一个缺口：ArcFace 指标记录缺失）

### 4. `数字人动作.md`（结构契约）

- `## 为什么重要`：动作自然度决定可看性；动作是分层递进的能力
- `## 现行做法（分层）`：①音唇同步（wav2lip→musetalk→vasa1 系）②**情绪与听态**（轴是情绪：音频不决定情绪、情绪怎么作为条件进来、expression_nr·expression_cls·THEval 等指标与 MEAD/RAVDESS/EMTD 数据集、听态双向生成）③手部与全身动作（co-speech gesture）；每层主流方法与代表工作（papers 库互链）
- `## 动作空间谱系`（**Blendshape 的深度内容在这里**）：表示谱系按「人能读懂多少」排列——3DMM 系数（BFM/FLAME，语义高）/ **Blendshape 系数（ARKit 52 维等，工业标准接口）** / **显式这一族要单独讲透（landmarks：68 点 iBUG 300-W / MediaPipe Face Mesh 468·478 / BlazeFace / 3DDFA 类 3D 关键点；参数化模型 FLAME、3DMM/BFM；标准接口 ARKit 52 blendshape；专门身份编码器 BlendFace；人工定义、可直接编辑、协议互不兼容）** / 部署运动向量（Ditto 265 维）/ 隐式关键点（LivePortrait，隐式 blendshape，无标注语义）/ latent（AF 20 维）；**必须写清显式与隐式关键点是两类表示**（有隐式就有显式）：显式语义明确但覆盖有限，隐式表达强但无天然语义、需靠扰动观察反推控制；讲语义可读性、训练来源、可控制性、跨软件通用性（引《动作空间专题》）
- `## 我们的工作`：
  - `### 中文音频适配（桥系列）`：蒸馏桥 → geom（单边 hinge，反塌缩）→ georkd（geom+RKD 关系蒸馏），附 LSE-C/LSE-D 与 sync_c/sync_d 指标表
  - `### 微调方法（Loss 与注入点）`：微调形态谱系（全冻结+桥 / LoRA / 单层解冻）与注入点审计方法；loss 设计如何影响音唇同步（引《微调策略专题》）
  - `### 情绪与听态`：以情绪为轴——情绪标签/情绪参考/语义与文本三条信号来源、情绪指标与数据集、AvatarForcing 的 Dual Motion Encoder 双向听态；Ditto 眼嘴四层拆分单列
- `## 可能的改进方向`：我们做到哪层、市面到哪层、下一步（听态质量、手部接入成本）

### 5. `工程设计.md`（结构契约）

**边界**：本篇写"**怎么设计的**"（链路与流程、设计动机与权衡、演进过程）；"**快不快**"归《数字人加速》，架构通论归《CyberVerse框架》，算法归《数字人动作》《数字人身份》。

**行文思路（本次重构）**：不再按"症状 → 修复"的排障叙事，改为按**设计**叙事——每一节先讲这段链路要解决什么、我们怎么划分职责与接口、为什么这么选、代价是什么，演进过程（含踩坑与回退）作为支撑材料而不是主线。

- `## 为什么重要`：工程设计决定可用性——模型只是链路一环；数据怎么流、资源怎么管、异常怎么接，决定能不能稳定跑起来
- `## 整体链路设计`：一次会话的数据流（音频输入 → 生成 → 贴回 → 编码 → 发布 → 浏览器播放），每段的职责、接口与衔接方式；**配图**：链路总图
- `## 贴回设计`：生成帧是裁剪区域，如何贴回原画面——完整链路六阶段（人脸检测与固定裁剪框 / 关键点检测 / 相似变换构造原图到裁剪的矩阵 / 逆矩阵贴回 / 羽化 mask 与 alpha 融合 / 只算人脸包围盒的性能路径）；三轮演进（接缝在脸周 → 对齐参考实现的 68 点裁剪 → 裁剪比例回退）；参数与验证方式（像素 max diff 为 0）；**配图**：贴回链路图
- `## 传输与发布设计`：帧从生成侧到浏览器——帧格式选择（YUV420 让载荷减半并去掉 CPU 色彩转换）、编码器常驻与关键帧重生、段聚合粒度、发布节奏（绝对播放锚点取代相对锚定）、缓冲档位；**音频缺口那一节按"发布节奏设计"来写**（段预算 200ms vs 固定等待 215ms 的设计缺陷 → 修复后 concealment 2.5–3.6% → 0.022%）
- `## 音频链路设计`：音频怎么进模型——分段与会话级差异、带下限归一化（防头部放大漂移的根因是逐块归一化把静默底噪放大到单位方差）、采样率与 offset 口径、待机静音流的设计（呼吸音的块间相位断裂与淡入覆盖）
- `## 会话与资源生命周期设计`：会话创建/回收/驱逐与三层兜底看门狗；idle 卸载；释放边界（插件每周期约 1.4GB 残留不能当作已解决）；进程 RSS 累积不归还的定位（基准路径对照证明泄漏在浏览器会话路径）；**配图**：生命周期图
- `## 稳定性设计`：打断与收声的状态机（尾音自然收住 → 聆听态 → 新话开始，含 4 版方案全部推翻的失败结论）、断连与恢复、非打断雪花帧、背压与限流（自锁问题 → 播放端存货判据 → 两级水位 / FLUSH / work-ahead 上限，标注进行中）
- `## 未采纳的设计方案`：降帧、深挖 GPU putback、把插件泄漏当会话问题解决

### 6. `数字人加速.md`（结构契约）

- `## 为什么重要`：实时性的两条天花板——**延迟**（用户等多久）与**吞吐**（能不能持续跟上）；"能用"的判据是首帧与持续帧率同时达标
- `## 实时性的三个指标与延迟链`：FPS / TTFF / RTF 各自的含义与关系；延迟链分解（音频窗口 → 模型推理 → 编码传输），并指出**音频窗口往往比模型推理更大**
- `## 生成侧加速`：视频推理加速作为独立一层——四类成本来源（注意力时空 token 近似 N² / 去噪步数 / 模型与显存 / 系统开销）+ **四个加速方向各成三级标题**（内核与稀疏 / 步数变少 / 缓存复用 / 并行与推理引擎，方向里点名 FPSAttention / BLADE / NAR / FlashAR / Latent Spatial Memory / WorldAttention / ZipAR / DAX / Inferix / TurboDiffusion）+ 两条结论（协同设计是唯一的免费午餐；训练费与即插即用光谱）+ 能落到我们管线的候选（LIA-X decoder 蒸馏）
- `## 系统侧加速`（我们的加速改进）：瓶颈基线（GPU 侧约 38.5ms/帧 vs 40ms 预算）+ Ditto 实时化三档（生产基线 / 已验证未默认 / 已回退）+ 编码与传输链路（常驻 NVENC、YUV420 传输、preset 分档、679ms 拆解）+ 首帧与开口（全链路首响应 3.5s → 2.9s、TTFF 与待机存粮、段聚合粒度）
- `## 模型实时性横评`：30+ 模型按路线分组 + 来源分级（论文披露 / 仓库 / 我们实测）；FPS 不能脱离 GPU 与分辨率比较；第一手 15+ 模型 SpeedRun / Formal Eval 数据位置待确认，取不到则该节标"待补"
- `## 硬件档位与可行性`：四个硬件层级；A10 结论表；**LiveAct 18B 的结论修正**（显存不是瓶颈、主机内存才是；Ampere 无 FP8；速度定位）
- `## 未采纳的加速方案`：降帧到 20fps、深挖 GPU putback、Warp TRT 与 LMDM FP16 未默认采纳等，附原因

## Decisions

- **D0 顺序与审核闸门**（依据 doc-writing skill）：
  0. **先 explore**：读该主题相关素材（knowledge/、CyberVerse @4968280、papers 库、任务树），搞清"这篇要写哪些章节、每章有什么内容可用"——**探索先于建 change**
  1. 建单篇 change：proposal / **design（内嵌完整大纲：文章有哪些章节 + 每章写什么内容 + 结论 + 引用关系）** / tasks
  2. **用户审大纲** ← 未过不放行
  3. 「资料整理」：抽取证据与数据表，**在对话中提交审核，不写入仓库**
  4. **用户审素材** ← 未过不放行
  5. 「动笔写作」：正文写进 `management/docs/实习复盘/<标题>.md`
  任一闸门未获明确确认，不得推进到下一步。
- **D1b 禁桶标题**：`## 现行做法` / `## 我们的工作` / `## 概述` 这类**分类名不许当标题**，其下主题直接写成二级标题（骨架只约束写作顺序，不约束标题结构）；主题自身横向展开时才用子节，且子节父标题必须是该主题的名字
- **D1 统一写作骨架**：内容文档按"为什么重要 → 现行做法 → 我们的工作 → 可能的改进方向"组织，避免写成单纯的改进流水账
- **D2 目录与命名**：子文件夹夹内平铺；单篇 change：复盘系 `docs-intern-<slug>`、笔记系 `docs-note-<slug>`
- **D2b 交付物位置**：**仓库里只保留文章正文**（`management/docs/...`）；计划（proposal/design/tasks）留在 change 目录；**素材/整理产物不进仓库**（按 D0 在对话中提交审核）
- **D3 正文不写出处**：文章正文**不写任何出处与素材指引**——不出现 `knowledge/xxx.md`、不写"《X》原文："、不标来源与日期、不标 commit。正文是给读者读的文章，不是带脚注的台账。
  - 出处、素材来源、代码 commit（`@4968280`）只保留在 **change 的整理环节与登记表**里，作为可追溯性；写完不进正文
  - 外部二手信息如果会影响可信度，用**自然语言**说明其性质（如"这是二手整理、未见官方数据"），而不是标出处
  - **例外**：本仓库文档之间的职责边界链接（"详见《数字人身份》"）保留，因为它承担结构分工，不是出处
- **D4 微调内容归属**：微调工作不单独成篇，按主题拆分——身份相关（ArcFace/ID loss 等）入《数字人身份》，音唇同步相关（geom/RKD loss、注入点消融、微调形态谱系）入《数字人动作》；无记录的口述实验标注证据状态，不编造数据
- **D7 实时性独立成篇**（本次新增《数字人加速》的理由与边界）：
  - **为什么拆**：实时性此前散在三篇里——《CyberVerse框架》写通论、《工程改进》写我们的改进、《数字人行业全景》写指标与横评，读者要跳三篇才追得完；更关键的是"**视频推理加速**"（模型侧的量化 / 稀疏 / 步数蒸馏 / 缓存 / 并行）当时**没有任何一篇承载它**，而它是实时性里独立且分量很重的一层
  - **边界（一句话）**：本篇只写"**快**"（延迟与吞吐）；"**怎么设计的**"（链路与流程设计、贴回、传输与发布、生命周期、稳定性）留在《工程设计》；原理与路线归《数字人介绍与技术路线》；市场与选型归《数字人行业全景》
  - **为什么按"快 / 稳与对"切**：这两条是**证据等级不同的线**——"快"可以用行业二手对比 + 我们自己的加速实测；"稳与对"几乎全是第一手故障排查。混在一篇会让证据等级互相污染，读者也分不清哪句是实测、哪句是行业现状
  - **搬迁规则**：从《工程设计》迁出瓶颈基线 / Ditto 实时化 / 编码与传输的性能数字 / 首帧与开口；从《数字人行业全景》迁出实时性三指标与延迟链 / 生成侧加速 / 模型实时性横评 / 硬件档位与可行性；迁出方删除对应内容只留一句链接（避免两处重复）
  - **位置**：排在《工程设计》之后（#6），因为读者先看"我们改了什么、踩了什么坑"，再看"速度这条线怎么系统化"
- **D6 图表规范（mermaid）**：架构 / 链路 / 流程 / 谱系类内容**必须配 mermaid 图**（表给细节、图给结构，不重复）；代码块标 `mermaid`，节点文本用双引号包住；单篇 1–3 张，放在对应小节开头
- **D5 数据诚实**：不编造数字；无把握处用自然语言写明（如「推测」「尚无实测」），不使用标注符号体系
