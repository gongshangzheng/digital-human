## 【待审核】正文大纲（11 节 / 3 张图）

### 一、`## 为什么重要`

- 实时数字人的可用性有两条天花板：**性能**（GPU 预算与发布节奏）与**稳定性**（会话与资源生命周期）。两者都不是模型问题，模型再好，卡顿与僵尸会话都会让产品不可用
- 这一篇的贯穿纪律：**局部阶段变快 ≠ 用户侧变快**。每次优化都要同时看阶段耗时、GPU 利用率、浏览器 fps、stall 与首帧（TTFF），不能只报一个 p95
- 边界：只讲我们改的部分与结论；通论见 [[实习复盘/CyberVerse框架|CyberVerse框架]]

### 三、`## 音频缺口修复`（跨端定位的样板）

- 现象：浏览器周期性音频缺口（听感是呲呲声）
- 定位：trace 显示发布端 `SendAVSegment` 有 **203–214ms** 背压，而每段时长 **200ms** → jitter buffer 耗尽，NetEQ 开始 concealment
- 根因：H.264 流编码器解析器持留段尾帧；旧逻辑在 `shortfall<=2` 时固定等 200ms grace → 真实 NVENC 编码约 15ms，加起来 **215ms**，刚好超过一段预算
- 修复两步：
  1. `shortfall==1` 视为确定性持留、立即返回，用 deficit 在下一段记账偿还（`shortfall==2` 保留 grace 兜底）
  2. 发布从"每段相对锚定"改为**绝对播放锚点**（deadline = 播放锚点 + 累计内容时长），单段超时不再逐段累加
- **数据**：cadence 1.056–1.070 → 1.018–1.020（稳态到 1.000）；send 段平均 203–214ms → 194–204ms；**concealment 2.5–3.6% → 0.022%**；浏览器 fps 23.5/min 22.6 → 24.5/min 24.4
- 结论（方法层面）：**症状在浏览器，根因在发布端**——把发布时长、cadence 与 concealment 放到同一条时间线上才定位得到；跨端问题先建能串起来的观测

### 四、`## 僵尸会话治理`

- 现象：浏览器被强杀后 terminal 路径可能不删 session，会话长期不退出
- 修复：三层兜底——terminal 路径补删除、idle 驱逐触发清理、peer 侧 30 秒连接看门狗
- **数据**：kill 后约 **29–31s** 进入 terminal、约 **35s** 会话归零、avatar backend 在 **3 分钟** idle 后卸载
- **边界（必须写）**：模型本体显存会释放，但 **AvatarForcing 插件每个 load/unload 周期仍残留约 1.4GB 活跃分配**——这是独立的插件泄漏，**不能把结果写成"GPU 归零"**
- **配图 3**：`flowchart TB` 会话生命周期与三层兜底时间线

### 四、`## PasteBack 贴回`（**本轮扩充：从"两条路径"改写为完整链路 + 三轮修复**）

- 问题：生成出来的是裁剪后的人脸区域（512×512），要贴回原画面；直接贴会出现接缝与亮度波动
- **完整链路（要分阶段写清）**：
  1. **人脸检测与裁剪**：检测器出人脸框（置信度阈值以上）→ 按 pad 扩框 → 得到固定裁剪框；**一旦确定，推理与贴回共用同一个框**（不重复检测，避免逐帧抖动）
  2. **关键点检测**：用 **68 点**（对齐 Ditto 之前是 5 点相似变换）——68 点覆盖下颌、额头、眉毛，外接框比 5 点大，且能给出瞳孔轴方向
  3. **相似变换构造 `M_o2c`**：由全脸关键点求 bbox → 中心（含水平/垂直比例偏移）、尺寸（正方形 × scale）、旋转角（瞳孔轴）→ 原图到 512×512 裁剪的仿射矩阵
  4. **逆矩阵 `M_c2o`**：对 `M_o2c` 取逆得到裁剪到原图的矩阵，贴回时用它把生成图与 mask 一起 warp 回原尺寸；Ditto 侧由注册环节维护该矩阵的列表并按帧取用
  5. **羽化 mask 与 alpha 融合**：矩形羽化 mask（中心为 1、边缘线性降到 0）→ warp 回原尺寸 → `生成 × mask + 原帧 × (1 − mask)`
  6. **性能路径**：GPU 帧管线里贴回 p95 **67.3 → 12.7ms**；并改为**只算人脸包围盒**，不再按源片全画幅（约 2.07MP）做两次 warp 加全画幅混合
- **三轮修复（本篇的叙事主线，按"症状 → 根因 → 修复 → 验证"写）**：
  1. **接缝出现在脸周**：flow suppression 在五官框（detector bbox ×1.15）边界处产生 hard transition，动态区域被限制在脸中央；移除贴回路径的 flow suppression 后，运动交回整个 512 裁剪区，接缝从脸周移到裁剪边界
  2. **对齐 Ditto 的裁剪**：旧实现用 **5 点**相似变换（双眼、鼻尖、嘴角），只约束五官 → 裁剪区内人脸占比过大、接缝贴近脸，且随关键点抖动产生边缘波动；改为 **68 点**（face_alignment）+ Ditto 的相似变换估计，中心加 **vy_ratio = -0.125**（下移 12.5% 主动包含肩膀），再取逆得 `M_c2o`；配套实验矩阵（scale 2.3 / 2.8、mask_ratio 0.9 / 0.8）
  3. **crop_scale 从 2.3 回退到 1.9**：2.3 时裁剪框下边界切入肩膀，而稳定化带只覆盖裁剪区下方 30%，无法一致抑制肩膀运动 → 贴回后肩膀与原始帧错位；回退 1.9 后错位消失（RTF 1.250 → 1.200、fps 20.0 → 20.9、显存 2633 → 2680 MB，基本持平）。**结论：要放大裁剪框必须同步调整稳定化带的范围，而不是单纯放大 scale**
- **与 Ditto 的对照（要写）**：Ditto 没有 flow suppression，只用矩形羽化 mask 做 alpha 混合；它维护裁剪到原图的矩阵列表并按帧取逆矩阵贴回。我们的第二轮修复就是向这套做法对齐
- 参数（可写进正文）：crop_scale（默认 1.9）、vy_ratio（-0.125）、mask_ratio（0.9）、mask 类型（rect）
- 素材：`management/projects/digital-human/notes/avatarforcing-pasteback-fluctuation.md`（三轮修复全过程 + 实验矩阵 + 指标）、`models/avatarforcing/pasteback_utils.py`、`models/avatarforcing/model.py`（贴回矩阵构造与检测裁剪入口）、`models/ditto/core/atomic_components/{putback,source2info,avatar_registrar}.py`、Ditto 的 mask 工具
- **配图**：贴回链路图（检测 → 关键点 → `M_o2c` → 逆矩阵 → 羽化 mask → 融合）

### 五、`## 会话与内存`

- 推理进程 RSS 从 9.8GB 涨到 20.5GB 且会话结束后不回落，逼近 OOM 阈值（曾有一次 28.8GB 被 OOM 杀掉）；基准路径连跑 5 轮 RSS 恒定在 6.6GB 无增长——证明泄漏在浏览器会话路径而非推理路径，排查范围由此收窄
- 边界：插件每 load/unload 周期约 1.4GB 的残留是**独立问题**（见僵尸会话治理节），两者不能合并结论

### 六、`## 体验类缺陷`（t1–t25 里属"稳与对"的部分）

> 按 D7：**首帧与开口**（全链路首响应、TTFF、段聚合粒度）属速度，归《数字人加速》；本节只留正确性与体验缺陷。

- **打断与收声**：症状 → 定位（语音绕过门控导致模型内积压、epoch 硬切冻在末帧）→ 四组独立改动；**并保留"打断立即止声试了 4 版全部推翻"的失败结论**（判据是人眼与听感，不是指标）
- **待机与静默**：呼吸音（100ms 块从 t=0 重生成 + 250ms 淡入覆盖整块，块内标准差 0.00118 vs 一次性生成 0.0133）；非打断说话的单帧雪花（码率漂移触发编码进程静默重生的嫌疑）；问候后无响应（上层语音服务断连 + 恢复未执行）
- **画质与流畅**：头部放大漂移（逐块独立归一化把静默底噪放大到单位方差 → 改带下限归一化）；周期性卡顿（窗口边界约 0.42s 出帧空洞，用约 500ms 语音预缓冲吸收）；输出比源视频糊的三层原因（输出高度上限、编码档位、码率下限）
- **限流阀重构（进行中）**：自锁问题、播放端存货判据、两级水位、FLUSH、lead 记账负值——多数仍在跑对照实验，只记当前认知

### 七、`## 未采纳方案与原因`

- 只改 `ditto.fps` 25→20：online 因果窗口与 audio2motion→warp 时序以 25 fps 为前提，纯配置降帧导致帧数与音频对应错位（实测 fps 18.8、min 14.4、stalls 3）
- 持续深挖 GPU putback / 微优化：GPU 饱和时没有端到端收益，应先减少 warp+decode 总工作量
- 把插件显存残留当作 zombie 已解决：两回事，泄漏需单独立项（每周期约 1.4GB）
- 结论：**负结论也是结论**——它们划出了"不要在这里继续投入"的边界

### 八、`## 可能的改进方向`

- 限流阀重构收尾（两级水位与 FLUSH 那套仍在跑对照）
- 插件显存泄漏单独立项（与会话生命周期解耦）
- 遗留 badcase 与优先级（雪花帧、问候后无响应、呼吸音的人眼复核）

### 九、`## 汇报要点`

- 一页可直取：瓶颈基线（38.5/40ms）、音频缺口三组数字（concealment 3.6%→0.022%）、会话回收时间线（+1.4GB 泄漏边界）、TRT 生产基线 vs 未采纳、贴回四项指标、未采纳三条

## Decisions

- **D1 素材不落仓库**：整理结果只在对话中提交审核；仓库只保留正文
- **D2 数字以实验记录为准**：冲突时取更接近实验记录的版本；**局部加速数据必须标注测量口径**，不得写成"用户侧变快"
- **D3 正文不写出处**：代码路径、commit、knowledge 路径只记在 change 的整理记录里
- **D4 不越界**：系统架构与实时性通论归《CyberVerse框架》；模型算法归论文笔记与《数字人动作》《数字人身份》
- **D5 配图 3 张**：实时管线与耗时标注图、两条贴回路径图、会话生命周期与三层兜底图（节点文本加双引号，放对应小节开头）
- **D6 标题规范**：不用桶标题（无"现行做法/我们的工作"）、标题不用冒号（用括号）、同文档内引用用 heading 链接

## Risks / Trade-offs

- [工程篇容易写成流水账] → 每节都按"症状 → 定位手段 → 结论/裁决"组织，突出定位方法与负结论，而不是罗列改了多少行
- [局部数据被误读成端到端收益] → 每个数字旁标注测量口径（隔离基准 / 模块 / 端到端），并把"局部变快≠用户变快"写成贯穿纪律
- [与《CyberVerse框架》重复] → 那边写系统通论与三条链路，这边只写我们改的部分与结论
- [t1–t25 里有多条 active] → 明确标注哪些是已完成结论、哪些仍在推进，不把进行中的写成已定论
