| 读者 | 用法 |

## 4. 完整章节结构（到三级标题）

### 4.1 标题下的无标题导语（**不单独立节**）

**要写什么**（三句，共约 250 字符，直接跟在 H1 后面）：

1. **范围声明**：领域内四篇主要综述都没有定义「数字人」，它们定义的是 talking head generation（三篇）与 human motion video generation（一篇），并把「数字人」当应用场景词（各出现 1–3 次）。本文沿用本仓库《数字人介绍与技术路线》的两分层（模型 / 系统）与两因素（动作 / 身份），范围划到**头 + 手 + 全身 + 双向交流**——因为领域里「头」与「全身」分属两篇不同综述，没有一篇同时覆盖。
2. **归类原则**：四个域各回答一个不同的问题（身份=还是不是同一个人、长什么样；动作=怎么动；实时性=跑得多快；路线=用什么手段），**子问题是开放集合**；另有一节「跨域问题」收不属于任何单一域的三类。
3. **写法**：直接论述问题——不引述本仓库笔记、不标注来源档位；数字只用于说明问题的规模与代价。

**不放**：领域重要性、文档价值论证、「为什么需要问题地图」——**这些全部删掉**。
**规模**：约 250 字符。

### 4.2 `## 一、身份`

#### `### 身份一致性：长视频为什么必漂`

**要论证**：身份一致性不是「像不像」的标量问题，而是三个独立难题叠加——**度量不统一、长时漂移、风格化失效**。
**证据**（素材清单，供写作者取用；数字为原始口径）：

| 证据点 | 出处 | 数字 |
|---|---|---|
| CSIM 五大缺陷（风格化失效、时序漂移、环境不鲁棒、长时身份演变、**度量循环性**） | 系列十八《身份一致性》 | 16 篇深读为证据 |
| 评测基准之间打架 | Face Consistency Benchmark | 6 个 FR 量尺分歧达 **2.7 倍**；「有锚/无锚」双协议**排名反转**；最强模型距真实视频仍差 **1.25–4 倍**；两种协议分数相差约 **3 倍** |
| **CSIM 的天花板** | Arc2Face | 纯 ArcFace 条件 + 2100 万图，未见 ID 的 CSIM 峰值 **≈0.85** |
| 风格化下 CSIM 失效 | StyleID | Cross-Method TPR **0.37 → 0.74**；手绘集 AUROC **0.9922** |
| 新度量路线 | ID-Sim | 49 个评测场景拿下 **48** 项第一 |
| 长时稳定的机制差异 | 系列五《扩散基模》、LiveAvatar、LeapTalk | LiveAvatar **10,000+ 秒**稳定（History Corrupt / AAS / Rolling RoPE，5×H800）；LeapTalk 用 reference 锚定的布朗桥把生成改成 data-to-data，长视频身份几乎不漂 |
| 多轮场景下的同一问题 | OmniMate | 用 MRCM（多参考图 + 参考语音）当**持久身份锚**，把「一段视频不漂」升级为「跨轮不漂」 |

**结论**：论文说「解决了身份一致性」时，说的是**自己协议下**的解决；跨论文比 CSIM 等于比不同的尺子。度量侧正从「FR 余弦」转向按感知/身份选择性训练的编码器。
**放进图中**：一条 Mermaid——同一句「身份一致」下的三条互不相同的失败（度量失效 / 长时漂移 / 风格化失效）。
**规模**：约 2,600 字符。

#### `### 多参考注入：从一张图到任意多角度`

**要论证**：身份注入的主线正在从「逐身份优化」转向「**一次前馈、任意数量无位姿输入**」，代价是训练算力与「专用化」。
**证据**：

| 工作 | 声称解决 | 机制 | 数字 |
|---|---|---|---|
| UIKA（CVPR 2026 Highlight） | 任意数量 **pose-free** 图像 → 可驱动 3DGS 头部 | UV 引导显式对应 + 双流注意力，一次前馈 | 渲染 **220 FPS**；7500+ 合成身份；**32×H20 × 2 周** |
| FlexAvatar | 1~4 张**无位姿**输入、无表情标签 | Head Query token 聚合 + UV 空间 UNet 解形变 | 重建 **0.4s**、驱动 **22ms/帧**（45 FPS）；2150 身份；10s 可选 refinement |
| CoFE / MoFE | **大姿态**下身份不「换人」 | ArcFace/CLIP/DINOv2 三专家 + 逐 DiT 层门控 | FaceSim-Arc **0.770/0.814**；+18.5% 参数；LaFID-180K |
| ConsisID | DiT 时代的身份注入失灵 | 按频率拆：低频 GFE 拼潜变量 + 高频双塔 cross-attn | FaceSim-Arc **0.58**（ID-Animator 0.32）；**+0.5B** 参数 |
| Arc2Face | 纯 ID 条件能把一致性推多高 | 用 ArcFace 嵌入替换文本条件 | 训练 **21M** 图 / **1M** 身份；用户研究 **71%** 胜过 InstantID |
| AniGS / LHM / MATCH | 单图或多视图 → 可动画资产 | 多视角生成 + 4DGS / 前馈 Transformer / registration-guided attention | AniGS ~**10 分钟**；LHM **2.01s**、PSNR **22.003**（AniGS 18.681）；MATCH **0.5s/帧**、45.3h → **4.63h**（**10×**）、570fps 渲染 |

**结论**：多参考注入的能力已经到「随手几张照片」，但三件事仍失守——**大姿态**（CoFE 存在的理由）、**风格化**（度量与身份定义同时失效）、**成本**（UIKA 的算力、FlexAvatar 的 scaling 曲线仍在上升）。
**规模**：约 2,500 字符。

#### `### 切分镜与多视角：换机位之后还是不是同一个人`

**要论证**：数字人交付里常有「切分镜 / 换机位 / 多视角」的需求；它的技术难点不在渲染，而在**跨机位（跨视角）的身份与外观一致性**——换机位之后还是不是同一个人、光照与背景是否连续。因此它归身份域：**能不能做**由路线决定，**判据与度量**属于身份。
**证据**：

| 层面 | 事实 | 出处 |
|---|---|---|
| **谁能换机位** | 3D 资产天然支持新视角合成——MATCH 在 **novel view synthesis** 上全面超越前作；LAM 是**纯 3D 管线、0 后处理网络**（**280 FPS**）；HyperGaussians **300 FPS**；参数化装配式（ARKit 52 + 游戏引擎）里多机位是传统图形管线的标配（我们未实测） | MATCH / LAM / HyperGaussians；系列四 |
| **谁换不了** | 2D 路线输出是**固定机位的人脸裁剪**：MuseTalk **256² 人脸区**；Talker-T2AV 以 **512² 为中间生成尺寸**再逐帧 FaceCropper 贴回源分辨率；Avatar Forcing / Ditto 同理。换机位 = 另生成一段新机位的片段 | MuseTalk / Talker-T2AV 精读 / 《工程设计》 |
| **多视角自身也会不一致** | AniGS 的观察：扩散模型生成的**多视角图像之间存在视角间不一致**，它把这种不一致当作「4D 高斯的时间维度变化」来处理 | AniGS |
| **视角是数据与生成里的显式变量** | MEAD **7 个同步视角**（60 人 / 281K clips / 39h）；NeRSemble-v2 **16 相机**（73fps / 7.1MP）；UIKA Synthetic **9 视角**（7500+ 身份 × 9 视角 × 13K+ 帧）；GenBench 把**视角**列为生成条件之一 | `knowledge/数据集整理专题` |
| **度量侧主动忽略了视角** | ID-Sim 的目标是「对背景/**视角**/光照**不变**」的身份相似度——即身份度量把视角差异当作**应当被忽略的干扰**，而不是需要度量的一致性；Face Consistency Benchmark 的双协议（有锚保真 / 无锚帧间相干）都只测**同一段视频内**，不测跨机位 | ID-Sim / FCB |
| **综述已把它列为独立质量维度** | FPSP v8 的十条质量维度里含 **「视角/几何一致性」**，并指出十条之间互相牵制 | 综述地图 |
| **我们的位置** | 单机位：生成帧是裁剪区域，再贴回原画面——换机位等于另生成一段 |

**结论**：切分镜/多视角在**能力**上由路线决定（3D / 参数化可换，2D 只能重生成），但在**问题**上属于身份——需要的是「跨机位仍是同一个人、且光照背景连续」的判据，而这个判据现在**不存在**：身份度量刻意对视角不变，现有基准只测同段视频内。这与《介绍与技术路线》里「表现范围」没有通用量化指标是同一处空白的两个侧面。
**规模**：约 1,700 字符。

#### `### 说话风格：从几张图或一段视频学到「这个人怎么说话」`

**要论证**：这一条现有三个入口，各自解决「风格从哪来」，**都不解决「风格与身份解耦」**。
**证据**：

- **几何解耦入口**：MakeItTalk —— 把输出压到 **68×3** landmark 相对位移，用 voice conversion 把音频拆成 content（说什么）/ speaker（谁在说）；只在真人数据上训练却**零样本**驱动油画/素描/日漫/卡通；28 FPS；**6480** 条 MTurk 响应
- **显式风格条件入口**：CapTalk —— 首个文本引导风格化的 3D 说话头；CapTalkingHead **24,441 clips / 200.8 小时**多模态风格标注；多尺度二值量化 Codec + T5 文本条件自回归；LVE **6.44**、FFD **25.14**；User Study 对 SelfTalk 偏好 Sync 92% / Style 96% / Expression 98%
- **few-shot 适配入口**：EmoTaG —— **5 秒**个性化视频、**11 分钟**适配、**76.4 FPS**、60K FLAME-Gaussians；情绪运动来自 GRMN + Semantic Emotion Guidance
- **风格化域的数据与评测**：ToonTalker（跨域卡通-真实双向重演）、Co-Speech NPR（非真实感角色）、GenEAva（135 类细粒度表情数据集）、系列十三（风格化评测方法论）
- **风格作为前缀**：Talker-T2AV 的 `--gt-prefix-seconds`（N>0 时用参考音频 + motion 前 N 秒借用韵律、节奏、头动风格）

**结论**：「学说话风格」目前**不是**一个被解开的单一问题，而是三条互不通用的技术：几何解耦换跨域能力、文本条件换可控性、few-shot 适配换数据效率。共同缺口是**风格与身份的混淆**，以及风格化域没有可信的身份/风格度量。
**规模**：约 2,200 字符。

#### `### 风格化：跨风格评测与风格化程度`

**要论证**：卡通/风格化不是“一个身份定义问题”，而是一组问题——**跨风格统一基准缺失、风格化程度无法连续度量、指标本身不风格感知**。
**证据**（系列十三，8+ 代表工作）：跨风格统一评测基准尚未出现（THEval 的运动特征统计量思路是起点，但需跨域关键点检测与风格适配）；**风格化程度的连续评估**（从“轻微风格化”到“高度抽象卡通”是否存在可比较的度量）；指标的风格感知改造（FID 用 Inception-v3 特征，能否换成卡通/动漫域训练的视觉编码器）；User Study 标准化（被试数从 **9 到 48** 差异极大，量表从二分类到 5 级 Likert，远低于图形学推荐的 30+）；恐怖谷与卡通的关系（何种条件下“不完美”反而增加吸引力）；另参见 CapTalk（**24,441 clips / 200.8 小时**多模态风格标注）与 ToonTalker（跨域双向重演）、GenEAva（135 类细粒度表情）。
**结论**：风格化把身份域的头两个问题（**定义**与**度量**）同时放大：在卡通域里 CSIM 失效（见上节）、FID 失去意义、User Study 口径不统一——所以它不是“身份定义”一节的附注，而是一组独立缺口。
**规模**：约 1,500 字符。

#### `### 这一块的未解问题`

**要论证**：把前面各节收成一张缺口清单。
**必须写到的九条**：① 统一身份度量（表示 / 监督信号 / 评测协议三个轴上的空位）；② 长时漂移的端到端机制（历史状态、参考锚点、位置编码、误差抑制四件套）；③ **跨轮一致性**（多轮对话中身份不漂，目前只有 MRCM 这类单点做法）；④ 大姿态；⑤ 风格化下「身份」的定义本身；⑥ 多参考「几张才够」的判据缺失；⑦ 风格与身份的显式解耦；⑧ **跨机位一致性**——切分镜/多视角缺的不是渲染能力，而是「换机位仍是同一个人」的判据（身份度量刻意对视角不变，基准只测同段视频内）；⑨ **风格化自身的度量**——无跨风格统一基准、无风格化程度度量。
**规模**：约 1,200 字符。

### 4.3 `## 二、动作`

**归类原则（要写进正文，代替「N 个子问题」这类固定数目）**：四个域各回答一个不同的问题，**子问题是开放集合**——会随调研继续增加，所以正文**不写「有几个子问题」**，也不给编号清单。

| 域 | 回答的问题 | 收录判据 |
|---|---|---|
| 身份 | **还是不是同一个人、长什么样** | 一切关于身份/外观（含多参考、跨机位、跨轮、风格、度量）的问题 |
| 动作 | **怎么动** | 一切行为侧的量（口型、表情、情绪、手、全身、双向反应） |
| 实时性 | **跑得多快** | 延迟、吞吐、长时稳定、资源 |
| 路线 | **用什么手段** | 各技术路线各自的承诺与代价 |

**子问题按门槛逐级抬高排列**（不按发现顺序，也不简单追加到末尾）。七级难度梯度：

| 级 | 难在哪 | 本文节 |
|---|---|---|
| ① **口型** | 从音频直接可推，最低门槛 | 音唇同步 · **跨语言适配**（同一级：换的是音素↔口型的映射与判据） |
| ② **整张脸** | 同步指标达标 ≠ 脸活着 | 整体面部动力学 |
| ③ **表情** | 从“有表情”到“对”到“能拧” | 情绪匹配 · 情绪控制与可编辑性 |
| ④ **语义** | 情绪语义→指代/意图语义，缺 grounding | 语义 grounding |
| ⑤ **双向** | 从“一个人演完”到“两个人互动” | 双向交流 · 反应性与听态 · 打断与回合边界 |
| ⑥ **人** | 发言权归属从双人扩到多人 | 多人场景 |
| ⑦ **部位** | 跨部位协调 + 容量/数据/评测三重代价 | 手部与全身 |

**规则**：新增子问题时先判它落在哪一级，**插到对应位置**，不追加到末尾；同一级内部再接“从易到难”。把双向交流算作动作问题的理由：它解决的是「数字人在一轮对话里**怎么动**」。

**同理**，身份域与实时性域也按难度排列（身份：一致性 → 多参考 → 跨机位 → 说话风格 → 风格化；实时性：延迟链 → 加速手段 → 长时生成 → 分段边界）。

#### `### 音唇同步：嘴对得上为什么仍然难`

**要论证**：口型是唯一能从音频**直接推断**的动作量，但它仍然难——难在**训练目标**（捷径学习）、**多目标拉锯**（同步 / 画质 / 身份）、**评测失效**。
**证据**：

| 问题 | 工作 | 声称的解法 | 数字 |
|---|---|---|---|
| 真实场景大量 out-of-sync | Wav2Lip | 预训练唇形专家判别器（SyncNet）当监督 | — |
| 同步 / 牙齿清晰度 / 身份互相打架 | MuseTalk | latent inpainting 局部重绘 + 两阶段训练 | **30 FPS** on V100；256² 人脸区；90h × 8×H20 |
| **捷径学习**（模型从视觉推视觉） | LatentSync | StableSyncNet（只含唇形-音频关联的嵌入）+ TREPA | SyncNet 准确率 **94%**；HDTF Sync_conf **8.9**、FID **7.22** |
| 稀疏 landmark 丢信息 | Flow-Guided | 3DMM 参数生成稠密光流替代 sparse landmark | 首个 **512×512** one-shot；AV Confidence **5.166**（Wav2Lip 5.227、MakeItTalk 2.770）；开源 **16h HDTF** |
| 音频该驱动哪部分没拆开 | Hallo | HADVS 把音频-视觉对齐拆成 lip / expression / pose | HDTF FID **20.545**、Sync-C **7.750** |
| 非正面视角 / 动态前景 | Hallo3 | 预训练 DiT 视频基座 + Identity ReferenceNet | HDTF FID **20.359**；64×H100；Wild 主体动态度 **13.286** |
| **指标本身失效** | THEval | 八大指标重做评测 | FID/FVD/SyncNet 全部与人类判断不相关（Spearman）；17 模型 × 5011 视频；发现「Wav2Lip SyncNet 悖论」与音频驱动头部运动僵硬 |

**结论**：同步数字不可横向比——换口径不可比（LSE-C/D vs sync_c/d），且**先确认时间对齐（offset）再比指标**；所有生成方法存在系统性一帧延迟（AV Offset −2）。真正的剩余难点不是「对不上」，而是**同步与画质、身份三者同时达标**。
**规模**：约 2,000 字符。

#### `### 跨语言适配：口型与同步是不是语言的函数`

**要论证**：同步与口型的判据大多在**英语语料**上训练，换语言会不会失效是一个被忽略的问题。
**证据**：Loss 综述的开放问题原话——「SyncNet 在英语数据（LRS2）上训练，对中文、日语等语言的同步判断可能不准。是否需要为不同语言训练专门的 SyncNet？或者设计语言无关的同步损失？」；我们自己的经验也指向同一处：原模型**听不懂中文音频**，眼嘴也分不开，靠「蒸馏桥 + 几何约束 + 关系蒸馏」才解决，同步指标优于对照锚（多域 257 clips）。
**结论**：这是一个「**评测与模型双双英语中心**」的问题——**指标**可能误判非英语语种，**模型**可能缺少音素覆盖；两者都要显式处理，不能靠 fine-tune 撞。
**规模**：约 1,200 字符。

#### `### 整体面部动力学：口型对了，脸为什么还是假`

**要论证**：口型只是**最低门槛**；真实说话含眼动、眉毛、脸颊、下巴、头部微动与停顿节奏。只对齐嘴部而其余区域静止，用户仍然觉得假。
**证据**：实时综述问题一原话就叫「口型对了，脸为什么还是假」；列出的量是眼动、眉毛、脸颊、下巴、头部微动与停顿节奏；Wav2Lip 类路线只解局部嘴型，其他区域静止时用户仍觉得「嘴在动，脸没说话」——这正是 **VASA-1（整体面部动力学，512×512，**40 FPS**）、Ditto（265D 运动表示含头姿与表情）、ChatAnyone（上半身互动）**继续建模整体动态的原因；Hallo 的 HADVS 把音频-视觉对齐拆成 **lip / expression / pose** 三路也是对同一问题的回应；THEval 发现音频驱动方法普遍存在「**头部运动僵硬**」，是这一问题的量化后果。
**结论**：这是一个“看似已解决”的伪完成问题——**同步指标达标不等于脸部活着**。
**规模**：约 1,300 字符。

#### `### 情绪匹配：表情跟不跟说得内容走`

**要论证**：情绪匹配有两条路——**（a）音频韵律 → 情绪运动**（有人在解）、**（b）说的内容 → 情绪**（几乎是空的）。并给出一个明确判据：Avatar Forcing 的条件三元组里没有任何语义通道，所以「平静语调说悲伤的话」它无法知道该悲伤。
**证据**：

- **数据集起点**：MEAD —— 60 演员 / **8 种情绪** / 3 级强度 / 7 视角 / **281K** 片段，情绪可控 baseline
- **（a）路线代表**：EmoTaG（情绪语音 → 上半脸 / 下颌 / 口腔运动带情绪变化，GRMN + Semantic Emotion Guidance）；SentiAvatar（plan-then-infill 把**语义规划**与**语音节奏**拆开，SuSuInterActs **21K** clips / 37h、200K+ 预训练 motion、**0.3s 生成约 6s**）；EMO-Avatar（LLM Agent 编排情感理解 + 三阶段咨询策略 + TTS 副语言控制）
- **说-听统一**：UniLS —— 解决 **listening stiffness**（听者僵硬）；两阶段（无音频先验学习 + 双轨音频微调）；听者分布指标 +**44.1%**，F-FID **13.143 → 4.304**（−67.3%）；**560.6 FPS**；但复现发现「越靠分布形状的指标越偏」（L_JDD +14.2%）
- **（b）路线现状**：`knowledge/音画同步专题` 与《数字人动作》均判定「**从说的内容推断情绪**」这条公开工作**很薄**；语音侧并行线是对比式 TTS 已支持 inline 控制 emotion 与韵律

**结论**：情绪匹配当前等于「**韵律匹配**」；真正意义上的「内容-情绪对齐」缺少输入通道与评价口径，是本篇要明确点出的一个领域级空白。
**规模**：约 2,000 字符。

#### `### 情绪控制与可编辑性：把情绪拧进去的通路`

**要论证**：控制信号按来源只有三条，控制粒度**与表示的语义可读性正相关**；隐式表示必须先靠扰动反推控制维度。另外要说明：「情绪控制」只是**可编辑性**（在综述里被当作一级类）里的一维——还有注视、眨眼、头姿、风格、强度。
**证据**：

| 通路 | 机制 | 代表工作 | 粒度与代价 |
|---|---|---|---|
| **情绪标签** | clip 级情绪条件，与音频、眼部状态并列 | Ditto | 粗（clip 级）；不能逐句变 |
| **情绪参考** | 借一段带情绪的参考视频/图 | 多模态控制类工作；Talker-T2AV 的参考前缀 | 中；依赖参考质量 |
| **可编辑中间表示** | 把可读的参数变成扩散条件 | FLAP（**120D** FLAME 系数当条件，Progressively Focused Training 解耦 pose/expression，Audio-to-FLAME）；EchoMimic（音频 + 可编辑 landmark 双驱动，3 种驱动模式，RLS 随机 landmark 丢弃，540h / 8×A100）；PerformRecast（改 3DMM 关键点变换公式，真正解耦表情与头姿，49 显式 3D 关键点，6 FPS） | 细（可逐维编辑）；需要拟合与渲染器支持 |
| **文本指令** | 用文字描述风格 | CapTalk；LIA-X（稀疏运动字典 + edit-warp-render，~1B 参数） | 细但语义-参数映射不稳 |

**结论**：可控性不是「有没有开关」，而是**表示给了多少可读的维度**；隐式表示（LivePortrait / Ditto 的隐式关键点）靠**逐维扰动观察画面变化**反推控制映射——这是工程上的必要手续，不是实现细节。
**边界**：THG Taxonomy 把 **Editing 当作一级类**，所以这里只拿情绪做例子；注视/眨眼/头姿/风格/强度的可编辑性归在同一条问题下，但正文不给子清单（子问题是开放集合）。
**规模**：约 1,900 字符。

#### `### 语义 grounding：动作怎么跟「说的内容」对上`

**要论证**：手势不是随机摆动——点头、摊手、强调、停顿与目光方向应与语义一致；当前动作主要由**韵律、风格与历史运动**驱动，不是语义理解。
**证据**：Avatar 综述原话「**动作生成还没有真正理解语义**」，真实 avatar 应理解「这里 / 那边 / 这个数字很大」这类**指代**，并与语言、场景对象、视线、手势 grounding 结合；实时综述问题三：「从 LLM 文本和语音 prosody 生成语义手势」**没有形成通用标准**（ChatAnyone 把上半身动作纳入实时数字人只是起步）；手部综述将「语义驱动手势」单列为开放问题（PersonaGest、SemConFlow 开始探索）；SentiAvatar 的 plan-then-infill 是最接近的做法——把**语义动作规划**与**语音节奏对齐**拆开（SuSuInterActs **21K** clips / 37h / 200K+ 预训练 motion）。
**与「内容-情绪对齐」的区别（要写清）**：那个问的是「这句话该是什么情绪」；这个问的是「**这句话在指哪个对象、哪一步该做哪个手势**」。
**结论**：和情绪一样，**缺的是输入通道**——语义要么走文本/LLM，要么走场景 grounding，两者都还没成为标准条件。
**规模**：约 1,500 字符。

#### `### 双向交流：为什么「能回应」不等于「在交流」`

**要论证**：绝大多数数字人的条件里只有**自己的音频**，所以只能生成「单向回应」，无法对用户做出反应——这是「没有互动感」的根因，不是画质问题。
**证据**：Avatar Forcing 的动机原话是现有模型「无法传达真正交互式交流的感觉，常常生成缺少情感投入的单向回应」，并把它归成两个挑战（因果约束下实时；无标注学出鲜活反应）。三条既有双向尝试的局限：DIM（**需人工切换角色**）、INFP（双向 DiT，**需完整时序窗口**，>3s 未来上下文，故不实时）、ARIG（仅表情层、时序差）。
**结论**：双向交流的第一个问题是**输入通道**——用户的音频与画面必须进条件，否则再好的模型也只能自说自话。
**规模**：约 1,000 字符。

#### `### 反应性与听态：用户的状态怎么进条件`

**要论证**：把「用户正在做什么」编码进条件后，数字人才能对用户反应；并且有一个**免标注**的办法学出更生动的反应。
**证据**：

| 机制 | 工作 | 细节与数字 |
|---|---|---|
| 用户音频 + 用户动作进条件 | Avatar Forcing | 条件三元组 `c=(a_u, m_u, a)`；Dual Motion Encoder 两级 cross-attn 把三路多模态输入编码成**同一种条件**；消融**去掉 `m_u` → 反应退化为静态** |
| 反应性度量 | Avatar Forcing | rPCC-exp / rPCC-pose：用户与 avatar 表情/头姿的**残差相关**；表现力用 SID / Var；人类偏好研究五项指标整体 **>80%** |
| 免标注学「更生动」 | Avatar Forcing | 用**丢掉用户条件**的输出构造 preferred / less-preferred 对做 DPO，不需要人工偏好标注 |
| 听态专门模型 | UniLS | 两阶段（无音频先验学习 + 双轨音频微调）解决 **listening stiffness**；听者分布指标 **+44.1%**，F-FID **13.143 → 4.304**（−67.3%）；**560.6 FPS** |

**结论**：反应性在**机制**上已被解（用户状态进条件 + 偏好学习提生动度），但**度量口径仍弱**——rPCC 衡量的是「跟用户同步」，不等于「反应得体」。
**规模**：约 1,600 字符。

#### `### 打断与回合边界：级联管线为何做不到双向`

**要论证**：级联（ASR → LLM → TTS → Avatar）结构上做不到双向/全双工，因为每一级都要等上一级完成；而「一轮说到哪里停」是在有双向要求之后才成为问题的。
**证据**：系列十四的八个设计维度（级联 vs 端到端 vs 混合、Talk→Listen→See 交互层级、延迟预算与流式策略、打断与双工、记忆与人格、模块化与一体化、环境智能）；Wan-Streamer 用**单个因果 Transformer** 统一文本/音频/视频的输入与输出共六路（Thinker–Performer 流式推理：**160ms** 流式单元、模型侧 **~200ms**、总交互 **~550ms**、25 FPS）；Ex-Omni-2D 对话原生（VTP 视觉思维规划 + 16 码本 + 四阶段解耦训练，E2E RTF **1.293**）；OmniMate 指出 Avatar Forcing / Wan-Streamer / UniLS 生成的回应长度都是**预设**的，用显式**生成进度控制器（GPC）**处理开放式回合；我们的实测结论是**打断后立即止声四个版本全部被推翻**（画面冻结 / 长度难调 / 尾音被一起丢弃），判据是「正确性由人眼与听感决定」。
**结论**：打断不是「静音」这么简单，而是**语义 + 画面 + 音频**三方同时收敛的行为；回合边界是双向交互独有的控制问题。端到端统一回避了跨模块对齐，代价是身份与模块替换成本上升。
**不写**：工具增强与 Agent 能力（属能力扩展，不是动作侧问题）。
**规模**：约 1,700 字符。

#### `### 多人场景：谁在说、谁说给谁听`

**要论证**：现有工作绡大多数是**单人**（或严格双人）；多人场景引入三个新问题。
**证据**：UniLS 明说局限——框架针对**严格双人**对话设计，多人需要解决**注意力分配、轮流发言检测、多听者差异化反应**；HunyuanVideo-Avatar 用 mask + localized cross-attention 指定「谁被驱动」，说明多人归属仍靠**外部指定**而非模型理解；《介绍与技术路线》把「掩码局部多人控制」列为独立条目，也把它标为「依赖 mask、复杂互动未解」。
**结论**：多人不是把单人模型跑 N 遍——它是**发言权归属**问题（谁在说、谁在听、谁的画面该动），目前只有外部掩码这一种解法。
**规模**：约 1,100 字符。

#### `### 手部与全身：最后一块拼图`

**要论证**：手与全身是动作域里**代价最高**的一块（要换渲染后端、要动作数据、要吃实时预算），且当前三条技术路线各有硬伤。
**证据**（系列十七，15+ 篇）：

| 硬伤 | 具体事实 |
|---|---|
| **手部-面部无显式协调** | TalkSHOW 有身体-手部交叉条件，但面部与手部之间无显式协调；DiffSHEG 的**单向信息流**只是初步尝试（且仅限 3D 表情参数）；CyberHost 在 2D 用共享 U-Net + 区域掩码做**隐式**协调 |
| **全身分辨率瓶颈** | CyberHost 明确指出 **640×384** 下面部与手部占比过小，VAE 与 U-Net 建模能力受限，手部细节显著退化——这是**模型容量分配**问题，不只是分辨率问题 |
| **训练数据手部模糊** | Hand Clarity Score 是第一个系统性处理（依赖拉普拉斯标准差），但数据质量仍是根本瓶颈 |
| **实时与手部质量互斥** | UMo 达到 **44 FPS** 但输出 3D 运动参数而非像素；CyberHost 像素级**RTF ≈65**；ChatAnyone 声称 30 FPS 但用 warping GAN，手部质量受限 |
| **评测跨路线不可比** | 3D 路线用 FGD/BC/Diversity，2D 路线用 HKC/HKV/FID/FVD；Audio2Photoreal 的照片级人类研究表明 **mesh 评测可能高估质量** |

**结论**：手部/全身不是「多加一个部位」，而是要同时换渲染后端、换数据、换评测口径。我们的结论一致——短期内不划算，但它是与市面方案的主要差距。
**为什么这一节不能省**：领域里「头」与「全身」分属两篇不同综述（三篇 THG 系只管头，Human Motion Video Survey 才管全身），**没有一篇同时覆盖**——这正是《介绍与技术路线》里「唇、头、手势统一框架缺位」的来源。
**规模**：约 1,700 字符。

#### `### 这一块的未解问题`

**必须写到的七条**：① 内容-情绪对齐缺输入通道；② **语义 grounding 缺输入通道**（手势不认识「这里」「这个数字」）；③ 同步指标与人类感知脱钩（THEval 已证）；④ 情绪数据集以受控表演为主（MEAD/RAVDESS）与真实对话分布有差距；⑤ 手部与全身的「表情-手势-语音」**无一篇综述同时覆盖**，协调机制与评测口径双缺；⑥ **双向交流没有评测基准**——「像不像在交流」没有公认指标（rPCC 量同步、不量得体），打断的正确性判据停留在人工，回合边界刚被提出；⑦ 跨语言：同步指标与音素覆盖双双英语中心。
**规模**：约 1,100 字符。

### 4.4 `## 三、实时性`

#### `### 延迟链：实时不是一个 FPS 数字`

**要论证**：实时是五个环节之和；论文只报生成速度时，**不能推断可交互**。
**证据（延迟链各环节的原文数字）**：

| 环节 | 具体数字 | 出处 |
|---|---|---|
| 首帧延迟（TTFF） | Ditto **385ms**、Online RTF **0.895**、**10** DiT 步；Avatar Forcing **0.5s** vs INFP\* **3.4s**；OmniMate **3.49s** TTFF | 系列三、AF 精读、OmniMate |
| 逐帧 / 模型侧 | Wan-Streamer 模型侧 **~200ms**、总交互 **~550ms**、**25 FPS**、**160ms** 流式单元 | Wan-Streamer |
| 渲染器 | LIA-X decoder **333ms/帧**（A10, 512², bf16, batch=1） | Talker-T2AV 模型精读 |
| 端到端 | Talker-T2AV 历史冒烟 RTF **21.33**、峰值显存 **15.0GB** → 「能跑」≠「实时」 | Talker-T2AV 接入与验证 |
| 我们侧的口径 | GPU **38.5ms/帧 vs 40ms 预算（96%）**，因此「**局部变快 ≠ 用户侧变快**」 | 《数字人加速》 |

**结论**：报告实时性必须同时给出**音频窗口 / 首帧延迟 / 端到端链路**三项，否则不可比。
**规模**：约 1,600 字符。

#### `### 加速手段：从少步蒸馏到流式状态`

**要论证**：所有加速手段可归为五类，每类都有明确的质量代价。
**证据**：

| 类别 | 代表 | 加速数字 | 代价 |
|---|---|---|---|
| 少步 / 蒸馏 | LiveAvatar（DMD，14B → 4 步）、LeapTalk（布朗桥，**1 步 / 200 FPS / 15000×**）、SoulX-FlashHead（Oracle 蒸馏，**96 FPS** Lite on 4090，1.3B DiT） | — | 误差累积被放大（LiveAvatar 明言少步蒸馏会放大累积） |
| 流式状态与 Forcing | Self-Forcing、Neighbor Forcing（LiveAct，**20 FPS** 小时级）、Diffusion Forcing（Avatar Forcing） | — | Forcing 策略有三大陷阱；KV cache 无限增长 |
| 缓存与 KV | Avatar Forcing 双锚 KV（缓存上限 **M=38**）、LiveAct ConvKV | — | 长时必须做有界管理 |
| 动作空间替代像素 | Ditto **265D** motion、Teller RVQ motion token（**200ms chunk**） | — | 表达上限受表示约束 |
| 架构与工程 | LiveAct 3 步蒸馏 + **FP8**；EGSTalker **68.51 FPS**；LAM **280 FPS**（A100）/ 35 FPS（iPhone 16）；MATCH **570fps** 渲染；TensorRT | — | 精度/平台绑定；渲染器替换要动契约 |

**结论**：加速不是「更快的模型」，而是**少步 + 有界状态 + 契约可控的渲染器**三件事一起做；只做其中一件会换来别的代价。
**规模**：约 2,000 字符。

#### `### 长时生成：误差为什么会累积`

**要论证**：长时的敌人不是算力而是**自回归误差**；论文各自给了不同根因与对策。
**证据**：LeapTalk 指出 noise-to-data 范式「每段从高斯噪声重建」导致误差逐段累积（身份漂移、细节退化、口型含糊），改用 reference 锚定的 data-to-data；LiveAvatar 给出三个长时漂移根因 + History Corrupt / AAS / Rolling RoPE；LiveAct 给出 Forcing 三大陷阱 + KV cache 无限增长；OmniMate 把问题推到**开放式**（模型不知道说多久、何时回到聆听）用 GPC 显式进度控制；Avatar Forcing 承认 exposure bias 未完全解决。
**结论**：长时稳定性靠**机制四件套**（历史状态 / 参考锚点 / 位置编码重置 / 误差抑制），缺一件就漂；这套机制目前分散在各工作里，没有统一设计空间。
**规模**：约 1,400 字符。

#### `### 分段边界：chunk 接缝处的不连续`

**要论证**：流式生成必然分段，而**段与段的接缝**是独立于长时漂移的另一类缺陷。
**证据**：UniLS —— **100 帧 chunk** 边界处偶尔出现微妙的运动不连续；论文自己的说法是「chunk 级别建模大幅减少了误差累积，但**离散化的时序分割与人类面部运动的连续性存在张力**」；Avatar Forcing 用 **look-ahead mask（l=2）** 与 offset 机制、LeapTalk 用块间滚动、LiveAct 用 ConvKV 记忆，都是在处理时间接缝；我们实测里「生成帧是裁剪区域要贴回原画面」（《工程设计》贴回六阶段）是另一类接缝——**空间接缝**。
**结论**：接缝问题是**分段策略的固有代价**——段越短延迟越低、接缝越多；需要的是一套跨段的运动连续性约束，而不是更大的模型。
**规模**：约 1,300 字符。

#### `### 这一块的未解问题`

**必须写到的四条**：① 实时口径不可比（FPS / TTFF / 每帧 / 端到端混用）；② 少步蒸馏与长时稳定的矛盾；③ 并发与显存（A10 上大模型 **0.8–0.9 FPS**、主机内存要求 ≥110 GiB）；④ 「局部变快 ≠ 用户侧变快」。
**边界**：本节只讲「快不快」；双向交流（听态、打断、回合边界）属动作域子问题，见 §4.3。
**规模**：约 800 字符。

### 4.5 `## 四、路线`

> 这一节不回答「有哪几条路线」（那是《数字人介绍与技术路线》的活），而是回答**每一条路线在解什么问题、代价是什么、为什么不能互相替代**。路线划分沿用该篇的「动作生成 × 身份呈现」搭配法，不按任务名（lip sync / talking head / 3D avatar）划分。

#### `### 路线一 2D 换嘴 / latent inpainting：解「嘴」，不解「人」`

**要论证**：最低成本地把嘴对上，但只解嘴。
**要写清的事实**：Wav2Lip 用预训练唇形专家判别器（SyncNet）当监督，解决真实场景大量 out-of-sync；MuseTalk 走 latent inpainting，**30 FPS on V100**、只处理 **256² 人脸区**、两阶段训练把清晰度与同步性拆开。身份保住的原因是「**没碰**」——除嘴与下半脸，其余像素沿用参考帧。
**代价**：不负责头动、眼动、手势；动作范围受限；身体与场景动态完全不生成。
**为什么不可替代**：**视频配音**这个交付形态只有它成立——保留原视频的头动、眼动与场景，只重写嘴部；也是最低成本的同步链路验证档。
**规模**：约 1,100 字符。

#### `### 路线二 结构化动作策略：解可控性，不解画面上限`

**要论证**：把「怎么动」变成**可读、可编辑、可单独评测**的语义动作量。
**要写清的事实**：输出 SMPL-X / FLAME / MANO / VQ motion token 这类参数化动作；代表工作 EMAGE、Audio2Photoreal，EMO2 更进一步——**改变音频驱动上半身的因果顺序**：先从音频生成双手这个 **end-effector** 的 **134D MANO** 运动，再让视频扩散模型据手、身体关键点与参考图补全上半身。
**代价**：受**参数空间上限**约束——强情绪、眼神细节、细粒度肌肉变化与复杂风格化形象都会被压平；且输出是 motion 不是最终像素，仍需 renderer。
**为什么不可替代**：动作**跨软件通用**（同一套 motion 可接不同 renderer / 游戏引擎），并且**动作质量可以脱离画面单独评测**——这是其余路线都给不了的。
**规模**：约 1,200 字符。

#### `### 路线三 动作扩散 + 快速渲染器：解实时可控（我们这条线）`

**要论证**：在**低维 motion 上做扩散**，再接快速 renderer，同时拿到可控性与实时性。
**要写清的事实**：Ditto（**265D** 运动表示、**385ms** 首帧、Online RTF **0.895**、10 步去噪）；Avatar Forcing（FLOAT 空间 **20D** α 与 `r=Bα`、默认 **0.5s** 延迟，对比 INFP\* 的 3.4s）；Teller（RVQ 离散运动 token + AR Transformer，**200ms** chunk）；ChatAnyone（上半身实时互动）；renderer 侧 LivePortrait（隐式关键点 + stitching/retargeting）、LIA-X（稀疏运动字典 + flow-warp）。
**代价**：画面自由度低于整帧大模型；motion 表示与 renderer **强绑定**（换 motion 表示通常要换 renderer）；长时有漂移，需要额外的身份治理。
**为什么不可替代**：**唯一能在消费级 GPU 上同时做到"可控 + 实时 + 可换 renderer"的一档**；我们的整条链路（CyberVerse 插件体系）就落在这里。
**规模**：约 1,500 字符。

#### `### 路线四 视频基座与整帧生成：解画面上限与场景，解不了低延迟`

**要论证**：整帧生成让脸、身体、背景与场景在**同一个生成空间**里协同变化，画面上限最高，但实时化最难。
**要写清的事实**：OmniAvatar（Wan2.1 14B，音频打包后**逐像素、多层**注入 video latent，用 LoRA 保住文本提示控制）；HunyuanVideo-Avatar（多角色 + mask 指定被驱动者）；Hallo3（首个把预训练视频 DiT 当底座做肖像动画，解决非正面视角与动态前后景）；OmniMate（开放式实时交互，联合生成语音 + 动作音效 + 视觉）。
**离线 vs 流式的量化分界（很有说服力的一组）**：离线双向注意力模型的 TTFF 从**几十秒到 658 秒**（MOVA-360P **658s** / UniVerse-1 **143s** / Ovi-1.1 **114s** / LTX-2.3 76s / DaVinci-Base 45s，FPS 都在个位数以下），因果流式那一档在 **3.5 秒上下**（OmniForcing **3.51s** / OmniMate **3.49s**，FPS 24.83 / 27.64）——**同为"视频基座"，因果约束一加，这条鸿沟就是交互可用性的分界**。
**代价**：训练与推理都重；身份长在权重或 LoRA 里，换身份=换适配器或重训；实时化要靠蒸馏、缓存、稀疏帧或 motion-to-render 混合。
**为什么不可替代**：需要背景、场景、全身自由度或 prompt 控制时只有这一档；它也是整条"视频基座红利"进入数字人的主通道。
**规模**：约 1,700 字符。

#### `### 路线五 3D 资产：解身份复用与视角自由（学习式 / 参数化装配式）`

**要论证**：把身份做成**可复用资产**——这是本领域唯一"资产化"的一档，也是切分镜/多视角的天然承载者。
**要写清的事实**：
- **学习式（5a）**：身份训练进 3D 表示（3DGS / NeRF）。EGSTalker 用 agent-token 中介交互把音频驱动 3DGS 做到 **68.51 FPS**、训练 3.7h；LAM 从单图生成可动画高斯头，**纯 3D 管线、0 后处理网络**，A100 **280 FPS** / iPhone 16 35 FPS；HyperGaussians 把高斯扩展为高维多元高斯，**300 FPS**（512²）、即插即用；AniGS 把"多视角生成的不一致"重述为 4D 高斯重建，约 **10 分钟**；MATCH 用 registration-guided attention 把 avatar 创建从 **45.3h 压到 4.63h**；LHM 前馈 Transformer 把可动画 3D 人体从 **15 分钟优化压到 2.01 秒**。
- **参数化装配式（5b）**：身份在美术制作的 rig 与材质里，动作回归出 blendshape / FLAME 系数再交给游戏引擎渲染，接口标准（**ARKit 52 维**）。工业实时角色（虚拟主播、游戏 NPC）走得最多，我们未实测。
**代价**：学习式换身份=重训，资产有注册与维护成本，大姿态/遮挡/手指自交有风险；参数化装配式写实度靠美术资产、制作成本高。
**为什么不可替代**：**换机位、多视角、切分镜只有这一档天然支持**（3D 资产可换相机位姿；2D 路线换机位等于另生成一段）；也是身份真正"可复用"的唯一形态。
**规模**：约 1,600 字符。

#### `### 路线六 掩码局部多人控制：解「谁被驱动」`

**要论证**：多人场景下的**归属**问题——指定这一轮谁在说、谁的画面该动。
**要写清的事实**：HunyuanVideo-Avatar 用 mask + localized cross-attention 限定说话人；这条路线依赖**外部给定的 mask**，模型本身并不"理解"谁在说。
**代价与缺口**：mask 由外部提供，插话、多人同时反应、注意力转移这些真实互动都没有解。
**与动作域的分工**：动作域的「多人场景」讲**问题**（发言权归属、多听者差异化反应），这里讲**手段**。
**规模**：约 900 字符。

#### `### 路线七 T2AV 与端到端统一：改的是任务定义，不是同一条搭配的变体`

**要论证**：这一档与上面六条不在同一层面——它换的是**任务定义与系统形态**（谁决定说什么、音频与画面是否同源生成），所以单列。
**要写清的事实**：
- **T2AV（文本驱动音视频联合生成）**：输入是目标文本 + 参考音频（音色/韵律/风格）+ 参考 motion/视频，输出是**新语音 + 新视频**；参考音频**不是**逐帧驱动口型的目标音频。Talker-T2AV 用 Qwen3-0.6B 共享自回归骨干（patch 覆盖 4 帧，音频与运动 patch embedding 同位置相加）分出两条 CFM/DiT 头——语音头 **32 维 WhisperX-VAE** latent、运动头 **40 维 LIA-X motion** latent，两条 latent 序列都 **25Hz** 对齐；视频侧由 LIA-X 渲染，**333ms/帧**。它的价值主张是绕开"TTS 再驱动"的跨模块韵律对齐。
- **端到端统一**：Wan-Streamer 用**单个因果 Transformer** 统一文本/音频/视频共六路输入输出，**160ms** 流式单元、模型侧 **~200ms**、总交互 **~550ms**；Ex-Omni-2D 用视觉思维规划 + 16 码本 + 四阶段解耦训练做对话原生的视频回复。
**代价**：系统更重、调试边界更复杂、**不自动更实时**；模块可替换性急剧下降（级联里能单换 TTS 或换 Avatar，端到端不能）。本地对这一档只有过 smoke 级证据（RTF 21.33、显存 15.0GB），只能说明"能跑"。
**为什么单列**：它不是六条路线里某一档的搭配变化，而是**把"谁说、说什么、什么时候产声音与画面"整体重写**。
**规模**：约 1,700 字符。

#### `### 为什么这些路线不能互相替代`

**要论证**：四条绑定关系，决定了路线选择不是"哪个效果最好"，而是"你的约束允许你走哪条"。
1. **渲染器与输入契约绑定**：LIA-X 吃 **40D** motion、FLOAT/AF decoder 吃 512D appearance + 20D α、Ditto/LivePortrait renderer 吃 canonical keypoints——动作表示一换，渲染器跟着换。
2. **身份资产有注册成本**：3DGS/NeRF 换身份=重训；参数化接口只换一组系数；整帧基座换身份=换适配器或重训。
3. **端到端整帧没有可换的后端**：身份长在权重或 LoRA 里。
4. **交付形态不同**（最根本的一条）：单机位还是可换机位、单人还是多人、离线质量还是实时交互——这些差异不来自模型强弱，而来自路线本身。
**结论**：路线是手段，问题是目的；同一条问题可以由不同路线解，但**没有一条路线能同时解掉全部问题**。
**规模**：约 1,300 字符。

### 4.6 `## 五、跨域问题`

> 收录**不属于任何单一域、但决定「能不能真用」**的三类问题。**这一节的存在本身就是一条判断**：它们不是任一域的附属——硬塞进某个域会扭曲归类。

#### `### 数据分布：公开集与真实业务之间的缝`

**要论证**：benchmark 分数不能外推到业务；缺的是**业务分布测试集**。
**证据**：实时综述问题四——公开视频数据集通常不等于客服、直播、教育、会议、陪伴场景；多语种、方言、快语速、笑声、打断、沉默、侧脸、遮挡、低码率、移动端摄像头与弱网都会暴露问题；Meng et al. 把 **large-angle head pose、data bias、temporal consistency** 列为关键挑战；Zhang et al. 2021—2025 纵向分析显示**训练集与测试集开始分离**，评测正从 IID holdout 走向泛化、表现力与可控性；手部综述的「训练数据手部运动模糊（Hand Clarity Score）」是同一问题的另一面。
**规模**：约 1,300 字符。

#### `### 合规与安全：授权、水印、滥用与许可`

**要论证**：这是**唯一一条「不解决就不能上线」**的问题；它是合规与工程问题，不是模型精度问题。
**证据**：实时综述问题五——单图与语音驱动天然有 **deepfake** 风险；业务设计必须默认需要**肖像授权、声音授权、水印、生成标识、滥用检测与日志审计**；系统框架还要注意 **GPLv3 等许可证**约束，开源模型的**代码许可、权重许可、训练数据许可**要分别审查；FPSP v8 的十条质量维度含「**安全与负责任使用**」；Avatar Forcing 的局限里也列了伦理风险。
**规模**：约 1,200 字符。

#### `### 复现与口径：论文数字能不能对上`

**要论证**：领域缺少可复现的评测基础设施——**论文数字与可复现数字之间有一道缝**，直接影响选型与引用。
**证据**：UniLS 仓库三条 open issue **全部零回复**：（1）FLAME 权重命名与官方发布物对不上（`flame_2020.pt` vs `generic_model.pkl`）；（2）论文承诺的逐帧 FLAME **tracking pipeline 未随仓库发布**，导致「用自己的数据复现」这条路走不通；（3）用发布权重 + 官方 `eval.py` 跑完整测试集，**8 项指标里 4 项明显偏离 Table 1**，并连带追问 CFG 分支语义、F-FID/P-FID 协议与 Missing keys。我们的「未采纳与待复跑」清单（ExOmni-2D / MoDA / LiveAct / UniLS / Talker-T2AV 预处理）是同一现象的另一面。
**规模**：约 1,400 字符。

### 4.7 `## 问题总账`

**要论证**：把四域 + 跨域收成一张表，按「问题 → 当前最好水平 → 缺口 → 相关文档」四列。
**表行（按块分组；行数随问题清单增长，**不写进正文**）**：
- **身份**：身份一致性度量 · 长时漂移（单段） · 跨轮一致性 · 大姿态 · 风格化身份定义与风格化程度 · 多参考注入 · 跨机位一致性（切分镜/多视角） · 2D 路线跨机位重生成的连续性 · 说话风格学习
- **动作**：音唇同步 · 整体面部动力学 · 内容-情绪对齐 · 语义 grounding · 可控性与可编辑性 · 双向交流反应性 · 打断 · 回合边界 · 手部与全身 · 跨语言适配 · 多人场景
- **实时性**：实时口径 · 少步与长时矛盾 · 分段边界 · 并发与显存
- **路线**：2D 换嘴路线的交付边界 · 动作空间的表达上限 · 动作扩散与 renderer 的契约绑定 · 视频基座（整帧）的实时化 · 3D 资产的注册成本 · 参数化装配式的写实度与制作成本 · 掩码多人的外部依赖 · T2AV / 端到端的可替换性与实时化
- **跨域**：数据分布 · 合规与安全 · 复现与口径

**结论**：四块里真正**没有被任何工作解掉**的是三件——① 统一身份度量（含跨机位、跨轮两个方向）；② **内容与动作的对齐**（情绪与语义两条都缺输入通道）；③ 双向交流的评价口径。另一类不同性质的缺口是**合规与安全**：它不是算法问题，却是唯一「不解决就不能上线」的一条。
**规模**：约 1,500 字符。

## 5. 口径与取舍

**写作口吻（硬要求）**

| 规则 | 说明 |
|---|---|
| **直接论述问题** | 正文以「问题是什么、难在哪、现在解到哪一步」展开；不写「见《数字人身份》」「《数字人动作》判定…」「我们的实测里…」这类句子 |
| **不标来源档位** | 不区分「论文声称 / 我们的实测 / 未复现」；我们自己的结论直接当论述写 |
| **数字服务于说明问题** | 模型名与规模数字保留（它们让问题可感），但**不要求逐条对齐出处**，也不写成引用格式 |
| **下表「证据」块的用法** | 下方各节的「**证据**」块是**给写作者的素材清单**，不是正文要复现的引用格式；写作时从中取事实、用自己的话论述 |
| **内链只在一处** | 站内链接只出现在「问题总账」的最后一列（当索引用）；正文不加内链 |

**不写的内容**

- 不写产品与竞品（→《数字人行业全景》）
- 不写我们自己的工程实现与框架（→《工程设计》/《CyberVerse框架》）
- 不写指标计算原理与数据集清单（→《介绍与技术路线》+ `knowledge/评测指标专题`/`数据集整理专题`）
- 不写论文单篇的方法细节（→ `论文笔记/` 与 `knowledge/*模型精读`）
- 不写工具增强与 Agent 能力（→ `knowledge/tool-augmented-digital-human`；那是能力扩展，不是动作侧问题）
- 不做 SOTA 排名、不写「最好的模型是 X」
- **不写导语式论述**：全篇唯一非问题内容是标题下 3 句导语；不写领域重要性、不写「为什么要问题地图」、不做全文总结式回扣
- **不写固定数目**：正文不出现「四个子问题」「22 行」这类会随调研变化的计数；**域固定为四，子问题开放增长**（新增子问题时只加节，不改已有表述）

**术语一致性**：首次出现的缩写给全称（CSIM、TTFF、DMD、RVQ、T2AV、A2V、GPC、MRCM…）；模型名沿用同目录与 `knowledge/` 的写法（`Avatar Forcing`、`Ditto`、`Talker-T2AV`、`LIA-X`）。
