## Goals / Non-Goals

**Goals：** 把我们对数字人的工程设计讲成一条完整链路——整体数据流 → 贴回设计 → 传输与发布设计 → 音频链路设计 → 会话与资源生命周期设计 → 稳定性设计，每节都给出设计动机、方案与权衡。
**Non-Goals：**
- 不写速度与吞吐（瓶颈基线、TensorRT、编码耗时数字、首帧与开口）→《数字人加速》
- 不写架构通论（级联/端到端/混合、延迟从哪来）→《CyberVerse框架》
- 不写算法与微调 →《数字人动作》《数字人身份》与论文笔记
- 不写成排障流水账：症状与修复只作为"为什么这样设计"的证据

## 【待审核】正文大纲（10 节 / 3 张图）

### 一、`## 为什么重要`

- 工程设计决定可用性：**模型只是链路的一环**。数据怎么流、资源怎么管、异常怎么接，决定系统能不能长时间稳定跑起来
- 本篇的设计原则（一句话）：**以"段"为单位组织流水线**——每段有预算、有明确接口、有可回退的档位；链路稳定来自每段职责清晰，而不是某段特别快
- 边界一句话：设计看本篇，速度看《数字人加速》

### 二、`## 整体链路设计`

- 一次会话的数据流：音频输入 → 生成 → 贴回 → 编码 → 发布 → 浏览器播放，横切着会话与资源生命周期
- 每段的职责与接口：
  - **生成侧**：输出裁剪后的画面 + 贴回所需矩阵
  - **贴回**：把裁剪画面合成回原画幅，保证接缝与亮度可控
  - **编码**：常驻编码进程，按几何复用，段为单位出流
  - **发布**：按绝对播放锚点投递，浏览器以固定帧率消费
- 设计取舍：**段化**换来可缓冲、可打断、可切换输入；代价是引入段边界（后续几节的很多设计问题都源于段边界）
- **配图 1**：`flowchart LR` 链路总图（标出每段职责与横切的生命周期）

### 三、`## 贴回设计`

- 问题：生成出来的是**裁剪后的人脸区域**（512×512），要贴回原画面；直接贴会有接缝与亮度波动
- **链路六阶段**（按设计顺序写，不按调试顺序）：
  1. **人脸检测与固定裁剪框**：检测器出框 → 按 pad 扩框 → 得到固定裁剪框；**推理与贴回共用同一个框**（避免逐帧重检造成抖动）
  2. **关键点检测**：68 点（覆盖下颌、额头、眉毛，并能给出瞳孔轴方向）
  3. **相似变换构造原图到裁剪的矩阵**：由全脸关键点求 bbox → 中心（含水平/垂直比例偏移）+ 尺寸（正方形 × 比例）+ 旋转角
  4. **逆矩阵贴回**：对上面的矩阵取逆，把生成图与 mask 一起 warp 回原尺寸；参考实现侧由注册环节维护该矩阵并按帧取用
  5. **羽化 mask 与 alpha 融合**：矩形羽化 mask（中心为 1、边缘线性到 0）→ `生成 × mask + 原帧 × (1 − mask)`
  6. **只算人脸包围盒**：贴回不再按源片全画幅（约 2.07MP）做两次 warp 加全画幅混合
- **三轮演进（作为设计依据写，不展开排障过程）**：
  - 接缝最初出现在**脸周一小圈** → 根因是区域抑制在五官框边界产生硬过渡，动态区域被限制在脸中央 → 移除贴回路径的抑制，运动交回整个裁剪区
  - 接缝随后**贴近脸且随关键点抖动** → 根因是只用 **5 点**相似变换（双眼、鼻尖、嘴角）约束五官、裁剪区内人脸占比过大 → 改用 **68 点**并对齐参考实现的裁剪方式，中心下移 12.5% 主动包含肩膀
  - 裁剪比例放大到 2.3 后**肩膀与原始帧错位** → 根因是裁剪框下边界切入肩膀，而稳定带只覆盖裁剪区下方 30% → **比例回退到 1.9**（与上游一致）；指标基本持平（RTF 1.250 → 1.200、fps 20.0 → 20.9、显存 2633 → 2680 MB）
- **设计结 
- **配图 2**：`flowchart LR` 贴回链路图（检测 → 关键点 → 正变换 → 逆矩阵 → 羽化 mask → 融合）

### 四、`## 传输与发布设计`

- **帧格式**：从 RGB24 换到 YUV420——1080p 单帧载荷 6.2MB → 3.1MB，同时去掉每帧的 CPU 色彩转换（编码器直吃 yuv420p）
- **编码进程设计**：常驻编码进程（每几何一个长生命进程，消除每段约 450ms 的进程与 CUDA 初始化固定开销）；硬编替代软编（软编约 640ms/秒段逼近实时预算，且同码率画质更低）；打断时强制重生进程以保证关键帧；缓冲档位配置化
- **段与发布节奏设计**：
  - 段长按状态区分（待机 / 说话 / 爬坡 / 预缓冲），粒度已可配置
  - **发布锚点**：从"每段相对锚定"改为**绝对播放锚点**（截止时间 = 播放锚点 + 已发布内容累计时长）——设计目标是让单段超时不再逐段累加
  - **音频缺口的设计缺陷与修复**：解析器持留段尾帧 + `shortfall<=2` 固定等待 200ms grace，使真实 15ms 的编码变成约 215ms，刚好超过 200ms 的段预算 → jitter buffer 耗尽触发丢包隐藏。修复两步：`shortfall==1` 立即返回并用 deficit 下段记账偿还；发布改绝对锚点
  - 结果：cadence 1.056–1.070 → 1.018–1.020（稳态 **1.000**）、concealment **2.5–3.6% → 0.022%**、浏览器 fps 23.5/最低 22.6 → 24.5/最低 24.4
- **设计结论**：段化的代价是段边界，而**边界上的固定等待必须以"绝对锚点 + 记账偿还"的方式设计**，否则误差会逐段累积

### 五、`## 音频链路设计`

- **分段与归一化**：流式下逐 0.4s 块独立做音频归一化 → 静默期呼吸底噪（RMS≈0.02）被放大到单位方差，模型持续被大能量噪声驱动 → 表现为**头部逐渐放大的漂移**；改为**带下限的归一化**后消除
- **采样率与 offset**：固定采样率与 offset 口径是同步诊断的前提（音频与视频特征窗口的相对偏移必须先对齐，否则会把对齐问题误判成模型问题）
- **待机静音流设计**：静音 PCM 每 100ms 重新从 t=0 生成 → 呼吸包络永远走不完、每块字节完全相同；250ms 淡入又覆盖整个 1600 样本块 → 形成 10Hz 锯齿包络（块内标准差 0.00118，而一次性生成同样时长是 0.0133，差约 11 倍）。设计上应让静音流**跨块连续**，而不是逐块重置

### 六、`## 会话与资源生命周期设计`

- **三层兜底**：terminal 路径补删除 + idle 驱逐触发清理 + peer 侧 30 秒连接看门狗；实测 kill 后约 29–31 秒进入 terminal、约 35 秒会话归零、idle 3 分钟卸载后端
- **释放边界（必须写）**：模型本体显存会释放，但插件每 load/unload 周期仍残留约 1.4GB 活跃分配——**这是独立问题**，不能把结论写成"GPU 归零"
- **进程内存**：推理进程 RSS 从 9.8GB 涨到 20.5GB 且会话结束后不回落（曾有一次 28.8GB 被 OOM 杀掉）；基准路径连跑 5 轮 RSS 恒定在 6.6GB 无增长，证明泄漏在浏览器会话路径而非推理路径
- **配图 3**：`flowchart LR` 生命周期图（三层兜底 → 时间线 → 释放边界）

### 七、`## 稳定性设计`

- **打断与收声的状态机**：打断 → 尾音在 1.5s 内自然收住 → 转闭嘴聆听画面 → 新话开始，全程无冻帧；定位到两个设计缺陷（语音绕过门控导致模型内积压、epoch 硬切冻在末帧），修复拆成四组独立改动
- **一条失败结论要保留**：让"打断立即止声"（丢弃已排队的旧回复语音）试了 **4 个版本全部被推翻**（画面冻结、长度难调、尾音被一起丢弃）——说明这条链路的正确性判据是**人眼与听感**，不是单点指标
- **断连与恢复**：问候后无响应表现为上层语音服务断连、恢复流程未执行；设计上需要显式的重连与恢复路径，而不是依赖调用方重试
- **非打断雪花帧**：每轮正常说话必现一帧雪花，嫌疑集中在码率漂移触发编码进程静默重生、以及预缓冲空窗扰动连续码流
- **背压与限流（进行中）**：限流阀存在**自锁**——阀门等待的量只能靠被它拦住的东西推动（阀门等视频抵达才放量，而模型要有新音频才出视频）→ 表现为每 2 秒一次卡顿。后续把判据换成**播放端存货**（会随播放自然消耗）、引入两级水位（待机/说话）、说话开始与打断走 FLUSH、统一 work-ahead 上限；还发现 lead 记账会变负。多数仍在跑对照实验，只记当前认知

### 八、`## 未采纳的设计方案`

| 方案 | 为什么不采纳 |
|------|--------------|
| 只把帧率从 25 改成 20 | 在线因果窗口与时序以 25 fps 为前提，纯配置降帧造成帧数与音频错位（实测 fps 18.8、最低 14.4、stalls 3） |
| 持续深挖 GPU 回贴与微优化 | GPU 饱和时没有端到端收益，应先减少 warp 与 decode 的总工作量 |
| 把插件显存残留当作会话泄漏已解决 | 两者是独立问题；插件每周期约残留 1.4GB，需单独立项 |
| 单纯放大贴回裁剪比例 | 会把裁剪框推进肩膀，与稳定带不匹配 → 第三轮已回退到 1.9 |

### 九、`## 可能的改进方向`

- 限流阀重构收尾（两级水位与 FLUSH 那套仍在跑对照）
- 插件显存泄漏单独立项（与会话生命周期解耦）
- 遗留缺陷的人眼复核与优先级（雪花帧、问候后无响应、呼吸音）
- 贴回链路参数化：裁剪比例、垂直偏移、mask 比例与类型已可配置，下一步是把"裁剪框与稳定带联动"做成显式约束

### 十、`## 汇报要点`

- 一页可直取：链路设计一句话（段化流水线 + 每段预算与档位）· 贴回六阶段与三轮演进的设计结论 · 发布节奏设计（concealment 3.6% → 0.022%）· 音频链路设计缺陷（逐块归一化 → 头部放大漂移）· 生命周期与释放边界（1.4GB）· 稳定性设计里的 4 版推翻 · 未采纳四条

## Decisions

- **D1 素材不落仓库**：整理结果只在对话中提交审核；仓库只保留正文
- **D2 行文按设计叙事**：每节先讲"这段链路要解决什么、怎么划职责、为什么这么选、代价是什么"；症状与修复降级为证据，不做主线
- **D3 正文不写出处**：代码路径、commit、knowledge 路径只记在 change 的整理记录里
- **D4 边界**：速度与吞吐归《数字人加速》；架构通论归《CyberVerse框架》；算法归《数字人动作》《数字人身份》
- **D5 配图 3 张**：链路总图、贴回链路图、会话生命周期图（节点文本加双引号，放对应小节开头）
- **D6 标题规范**：不用桶标题、标题不用冒号、同文档内引用用 heading 链接
- **D7 迁移配合**：本 change 与 `docs-intern-acceleration` 的搬迁任务需同步——本篇删除性能与速度章节并留链接

## Risks / Trade-offs

- [改成设计叙事可能让"我们踩了什么坑"消失] → 演进与失败结论都保留（贴回三轮、打断 4 版推翻），只是放在证据位置

- [与《数字人加速》重复] → 本篇只写"设计怎么做"，速度数字只在必要处点一句并链过去
