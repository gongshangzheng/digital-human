### 三、`## 技术路线版图`
- 3.0 `> 框架说明`：**两个因素——动作与身份**
  - **动作**：怎么动（表情、口型、头姿、手势、身体）→ 由**动作生成**决定：模型直接预测什么
  - **身份**：长什么样、是不是同一个人（外观、纹理、几何）→ 由**身份呈现/渲染后端**决定：身份靠什么落地
  - 关键表述：**动作生成对应"怎么动"，身份呈现/渲染后端对应"身份怎么落地"**；两者的搭配受接口契约与身份资产成本约束，本文讲的就是这套搭配关系（见 3.3）
  - 源材料（《数字人基础》）用的说法是"生成方式 × 渲染资产后端"，本文把它精确化为"动作生成 × 身份呈现"，并显式写出搭配约束
- **完整路线清单**（依据 `digital-human-avatar-survey` 表 2 的六条 taxonomy + `数字人渲染器专题` §二的 renderer 谱系）：**表格列按框架拆成「动作生成 / 身份呈现」两侧**，让每条路线的两个因素分别可见

| # | 路线 | 动作生成（怎么动） | 身份呈现（怎么落地） | 代表工作 | 优势 / 限制 |
|---|------|------------------|--------------------|---------|------------|
| 1 | 2D talking-head / latent inpainting | 局部换嘴、视频级修正（landmarks / mask 驱动 latent inpainting） | 参考图或视频（2D warping，身份就是参考外观） | MuseTalk、SadTalker | 简单快、生态成熟 / 身体手势弱、3D 一致性弱 |
| 2 | 结构化动作策略 | 动作空间生成（SMPL-X、FLAME、MANO、VQ motion token） | 参数化渲染器（FLAME / 3DMM / SMPL-X） | EMAGE、Audio2Photoreal、EMO2 | 可解释可控、动作可单独评估 / 仍需 renderer |
| 3 | 动作扩散 + 快速渲染器 | 动作空间生成（低维 motion，扩散生成） | warping GAN 或 renderer（Ditto、LivePortrait、LIA-X、FLOAT/AF decoder） | ChatAnyone；**Ditto、Avatar Forcing（我们的主线）** | 实时性强、工程闭环清晰 / 画面自由度低于整帧大模型 |
| 4 | 视频基座模型适配 | 整帧视频生成（video latent、DiT/MM-DiT） | 身份靠参考图条件注入（ReferenceNet、LoRA）——动作与身份一起生成 | OmniAvatar、HunyuanVideo-Avatar、wan-streamer | 全画幅表达强 / 训练推理重、资产不可复用 |
| 5a | 3D 资产（学习式） | 动作空间生成（motion、pose） | 3DGS 高斯、NeRF 场（身份需先训练进资产） | GaussianTalker、UIKA、FlexAvatar | 身份可复用、渲染可控 / 注册难、训练成本高、极端动作风险 |
| 5b | **3D 资产（参数化装配式）** | 动作空间生成（**blendshape / FLAME 系数**） | **rigged mesh 美术资产 + 游戏引擎渲染**（ARKit 52 等标准接口） | FLAME/3DMM 系、Audio2Face 类 | 接口标准、可跨软件 / 写实度靠美术资产、制作成本高 |
| 6 | 掩码局部多人控制 | 整帧视频生成 + 局部控制（face mask、localized cross-attention） | 参考图条件 + 掩码限定说话人 | HunyuanVideo-Avatar | 可指定说话人 / 依赖 mask |

- 注：**Blendshape/FLAME 作为动作表示的深度内容在《数字人动作》**，这里只作为资产接口与后端出现，一句话 + 链接，不展开
- **必须辨析（易读歪点）**：FLAME / blendshape / 隐式关键点 / latent 是**动作表示**，属于「动作空间生成」的内部表示形式，**不是第四种生成方式**；它们同时出现在身份呈现后端里，是因为同一套参数化表示两用——既是动作生成要预测的目标，又是身份资产的驱动接口（如 FLAME canonical space 驱动 3DGS）。两因素说明下必须有一句显式辨析；5b 行的核心表示写成「blendshape/FLAME 系数 → 驱动 rigged mesh」，避免读成"blendshape 是一条生成方式"
- 3.3 **动作生成与身份呈现的绑定关系**（本次修正的重点，必须写清）
  - 渲染器与其输入契约绑定：Ditto/LivePortrait renderer 吃 canonical keypoints；LIA-X 吃 40D motion code；FLOAT/Avatar Forcing decoder 吃 512D appearance + `r=Bα`
  - 身份资产有训练/注册成本：3DGS/NeRF 必须先把身份训练进资产，换身份 = 重新训练；FLAME/ARKit 走参数化接口，换身份成本低
  - 端到端整帧视频生成不换后端（身份就长在模型权重/LoRA 里）
  - **结论**：动作生成与身份呈现的搭配受接口契约与身份资产成本约束，**不是任意搭配**；换后端要付出的代价，取决于身份表示的可复用性
- 3.4 `### 动作表示谱系`（**不能只写一行箭头**，要写成一张表 + 取舍 + 关键事实）
  - 前置一句：表示 = 模型输出用什么格式描述「怎么动」
  - **表**：表示 | 形式与维度 | 语义可读性 | 代表工作——至少覆盖 3DMM 系数（BFM/FLAME）、Blendshape 系数（ARKit 52）、部署运动向量（Ditto 265 维）、隐式关键点（LivePortrait）、整体面部 latent（VASA-1/FLOAT 512 维）、资产接口（SMPL-X/ARKit/BVH/motion token）
  - **两端取舍**：显式端可解释可编辑、能接工业管线；隐式端容量与上限高但不可直接编辑
  - **关键事实**：① FLAME 系数语义清晰、可作可控条件（FLAP）② FLAME 顶点自带 blendshape + LBS 权重，故 FLAME 系数能直接驱动 3DGS ③ 隐式表示可由小型 MLP 学出局部控制（Ditto 的 gaze/emotion/pose 控制）
  - 深度（四层拆分机制）留在《数字人动作》，此处只给谱系 + 链接
- 3.5 `### 渲染后端谱系`：**顺序为先动作表示、后渲染后端**（与动作/身份两因素的次序一致）；两节统一叫「谱系」，不用「光谱」
- 补充：**身份呈现后端视角**（`数字人渲染器专题` §二）——2D warping renderer（Ditto/LivePortrait、LIA-X、FLOAT/AF decoder）、FLAME/3DMM、NeRF/3DGS 专人资产、**ARKit/blendshape/game engine**、视频级后处理（Wav2Lip/LatentSync，非完整 renderer）；**这些后端解决的都是"身份怎么被保留并重演"**
- 论证/结论：路线分野在「中间表示 + 渲染后端」；同一任务可由多条路线完成；**「操控 3D 模型」（参数化/rigged + 引擎渲染）是独立且工业成熟的一条路线**，与 5a 学习式资产区分（5b 资产为手工/标准接口，5a 需训练）
- 素材：`digital-human-avatar-survey` 表 2、`数字人渲染器专题` §二/§三、`动作空间专题` 表示谱系

### 四、`## 评价体系`（原「评价口径」，扩写为独立章节）
- **术语先行**：正文开头先定义两个名词——**评价维度**（从哪个层面评，一组评价的骨架）与**评价指标**（用哪个数字量评，可测量的量）；下文标题用这两个词的全称，不用泛指的"维度/指标"
- 5.1 `### 三个评价维度`
  - 表：**维度 | 问什么 | 包含什么 | 常见误读**
    - 表现质量：像不像、自然不自然 | 画质、身份一致性、音唇同步、动作自然度、时序稳定（闪烁/抖动） | 只看单帧画质，忽视长时漂移与闪烁
    - 表现范围：能驱动到哪里 | 只改嘴 / 头肩说话 / 上半身手势 / 全身 / 带背景与多人 | 把任务名当能力边界
    - 工程性能：能不能用起来 | 首帧延迟、持续帧率、显存与 GPU、并发 | 拿论文 FPS 当产品准入标准
  - 结论：评方案先分清在看哪一层；三个维度不能混着比，也不能互相代替；任务名（lip sync / talking head / 3D avatar）是说表现范围或实现形态，被当成能力边界是常见误读
- 5.2 `### 五个指标族`（表头写「评价指标族」）
  - 表（代表指标 + 回答什么问题）：唇同步（Sync-C/D）、身份与长时漂移（CSIM/CSIM-drift/LPIPS-drift）、画质（PSNR/SSIM/LPIPS/NR-IQA）、时序流畅（Dino-S/flow_smoothness）、效率（FPS/TTFF/延迟/显存）
- 5.3 `### 评价维度与评价指标的对应`（表头：评价维度 / 对应评价指标族 / 量化程度）
  - 顺带点明两个因素与指标的对应：**动作** → 唇同步、动作自然度；**身份** → CSIM 身份一致性、画质；两者共同影响时序稳定
  - 把五族映射回三个评价维度：效率 → 工程性能；其余四族 → 表现质量的不同侧面（音唇 / 身份 / 画质 / 时序）
  - **指出缺口**：表现范围这一维度目前几乎没有通用量化指标，只能靠能力描述——这是评价体系自身的空白（我们的观察）
- 论证/结论：指标各有适用域；维度层比指标层更能指导选型
- 引用：链《数字人身份》看 CSIM 边界
