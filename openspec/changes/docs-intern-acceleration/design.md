## 【待审核】正文大纲（8 节 / 3 张图）

### 一、`## 为什么重要`

- 实时性有两条天花板：**延迟**（用户等多久——首帧）与**吞吐**（能不能持续跟上——持续帧率）。只满足一条都不算能用：高帧率但首帧 3 秒只适合离线，首帧很快但帧率 15 只适合低帧率交互
- 本篇的姿态：**"快"是可拆、可测、可优化的**，而不是"模型算得快就行"
- 边界一句话：本篇只讲快；稳与对见《工程改进》，市场见《行业全景》

### 二、`## 实时性的三个指标与延迟链`

- **FPS** 管持续流畅度（≥25 实时、≥50 才有余量做多路）；**TTFF / 首帧延迟**管交互灵敏度；**RTF**（处理时间 ÷ 音视频时长）是吞吐效率的综合度量，RTF < 1 表示跑得比实时快
- 三者必须一起看：这是判断"能不能用"的核心口径
- **延迟链分解**：音频窗口 100–2000ms → 模型推理 10–200ms → 编码传输 20–350ms；**音频窗口往往是最大项**，而论文最常优化的模型推理通常不是
- **配图 1**：`flowchart LR` 延迟链三段（标出大头在哪）
- 本节末尾自然引出两条加速路径：压模型推理 → 第三节；压其余两段 → 第四节

### 三、`## 生成侧加速`（**视频推理加速**）

- 定调：视频生成推理本身是一个可优化的层——算法与模型侧的加速手段
- `### 慢在哪`：四类成本来源——注意力（时空 token 近似 N²）、去噪步数（每步完整前向）、模型与显存（大基座与长序列）、系统开销（调度 / 通信 / 缓存 / 编解码）；**配图 2**：`flowchart LR` 四类成本 → 四类加速方向
- **四个方向各成三级标题**（不设四级、不逐工作展开，每个方向 1–2 句说明"做什么、属于哪一档"）：
  - `### 内核与稀疏` → FPSAttention（FP8 量化与稀疏注意力协同设计）
  - `### 步数变少` → BLADE（块稀疏 × 步数蒸馏）、NAR（邻域自回归）、FlashAR（后训练加速）
  - `### 缓存复用` → Latent Spatial Memory（隐空间空间记忆）、WorldAttention（缓存与计算协同）
  - `### 并行与推理引擎` → ZipAR（空间局部性并行解码）、DAX / Inferix（推理基础设施与引擎）、TurboDiffusion（模型与系统协同设计）
- `### 两条结论`：
  - **协同设计是唯一的免费午餐**——单点优化容易被别的阶段吃掉（与我们工程侧的"warp 变快但 stitch 抵消"是同一件事）
  - **训练费与即插即用的光谱**：零训练（ZipAR、DAX）→ 后训练（FlashAR）→ 蒸馏或量化感知训练（BLADE、FPSAttention、TurboDiffusion）→ 从头训练（NAR）；选型前先问"我们手里是完整训练链、部分微调入口，还是只有推理权重"
- `### 能落到我们管线上的`：**LIA-X decoder 蒸馏**（512² / bf16 / batch=1 约 **333ms/帧**，当时 T2AV 链路的速度瓶颈，属于只需推理权重那一档）；倍数可比性写进正文句子（同模型 / 硬件 / 分辨率 / 步数 / 质量约束，幻灯片与论文口径要对齐）

### 四、`## 系统侧加速`（我们的加速改进）

- `### 瓶颈基线`：GPU 侧 decode + warp + LMDM + stitch 合计约 **38.5ms/帧**，25 fps 预算只有 **40ms**（占 96%）→ 余量几毫秒，很多"变慢"其实是排队，不是模型慢；附阶段耗时表（decode 17.7 / warp 14.9 / LMDM 3.9 per 0.4s block / stitch 约 1ms）
- `### 推理侧加速`（Ditto 实时化的三档）：
  - **生产基线**：motion space + 分段流式 + 10 步去噪（定住生成侧上限）· Decoder FP16 TensorRT（隔离 73.5 → **17.7ms/帧**，约 4.2×）· 独立 CUDA stream 与 buffer 复用 · Warp→Decoder GPU 直传 + CUDA Event · LMDM 常量条件一次绑定（49 → 39ms）
  - **已验证未默认**：Warp TensorRT（14.9 → 11.8ms/帧，但 stitch 2 → 9ms 抵消，浏览器 fps 无变化）；LMDM FP16（8.35 → 3.27ms，生产 RTF 0.916 → 0.870，**浏览器 fps 23.8 → 23.9**）
  - **已回退或候选**：GPU putback、单 worker、降帧；DDIM 少步待验
  - 结论：各项的测量对象不同（模块耗时 / RTF / cadence / 浏览器体验），**不能相加成"总加速 N 倍"**；GPU 长期 90%+ 时 stream overlap 受同一批 SM 争用
- `### 编码与传输`：679ms 拆解（进程与初始化约 400ms + 色彩转换 90ms + 编码 40ms + 管道写入）→ 编码器常驻（消除每段约 450ms 固定开销）· H.264 换 NVENC 硬编 · YUV420 传输（1080p 单帧 6.2 → 3.1MB）· preset 随分辨率分档
- `### 首帧与开口`：全链路首响应 **3.5s → 约 2.9s**（首段 400ms 即发、预缓冲 800 → 400ms）· TTFF ≈ 排空待机存粮（≤1.12s）+ 首块推理约 0.3s · 段聚合粒度 1000/400ms → **200ms**
- **贯穿本节的一句判断**（与工程侧一致）：**局部阶段变快 ≠ 用户侧变快**

### 五、`## 模型实时性横评`

- 30+ 模型按路线分组，**每行标注来源类别**：论文披露 / 开源仓库 / 我们实测；未公开留空不猜
- **可比性前提（写进正文句子，不设"纪律"类小标题）**：FPS 不能脱离 GPU 型号与分辨率比较（同模型跨卡差异可达 5–10 倍）；表里的"实时 ✓"只代表该卡上 FPS ≥ 25 或 RTF < 1，**不代表产品级端到端实时**
- 代表数字（说明跨度）：SadTalker 消费级 5–15 FPS · LivePortrait 4090 67 FPS · Ditto（A100 + TRT）RTF 0.895 / 首帧 385ms · LiteAvatar A10 实测 25.19 FPS · **FlashHead Lite A10 实测 46.7 FPS vs Pro 1.3B A10 4.8 FPS**（同家族差近 10 倍）
- **第一手 15+ 模型 SpeedRun / Formal Eval**：位置待确认（决策点 3）；取不到则本节标"待补"，不用二手数字冒充第一手

### 六、`## 硬件档位与可行性`

- 四个档位：零 GPU / CPU / 移动端 → 单张消费级 → 单张数据中心（A10 / A100 / H100）→ 多卡；**配图 3**：`flowchart TB` 四档与可达能力
- A10 结论表：LiveAct 不适用（官方口径依赖多卡 + FP8）· LivePortrait 需实测 · Ditto 需实测（担心显存）· FlashHead Pro 已验证
- `### LiveAct 18B 的结论修正`（**值得单独写的一段，因为我们的结论被自己的复测推翻过**）：
  - 早期记"不可用（OOM / 超时）" → 两次完整跑通推翻
  - **显存不是瓶颈**：峰值只有 **10.4 GiB（512²）/ 11.7 GiB（416×720）**，22.5 GiB 的 A10 还剩一半
  - **主机内存才是**：offload 三件套后稳态约 **85–90 GiB**，正确口径是"整机独占 + 可用主机内存 ≥110 GiB"，且不能只看启动瞬间快照；此前失败是同机其它任务挤爆内存，不是 GPU OOM
  - **两条路走不通**：不加 offload 约 36 GiB 单卡塞不进；**A10 是 Ampere，没有 FP8 硬件**，砍 KV 方案作废
  - **速度定位**：约 **0.8–0.9 FPS**（55.5 秒视频要跑约 39 分钟），而小一个数量级的 FlashHead Pro 1.3B 是 1.4 FPS → 大模型在 A10 上没有质量红利，只适合离线
  - 证据边界：这两次跑的是 `audio_cfg=1.0`，**会跳过音频引导分支**，所以唇同步质量不可与其它模型横比

### 七、`## 未采纳的加速方案`

| 方案 | 为什么不采纳 |
|------|--------------|
| 只把 `ditto.fps` 25 → 20 | 在线因果窗口与时序以 25 fps 为前提，纯配置降帧造成帧数与音频错位（实测 fps 18.8、min 14.4、stalls 3） |
| 持续深挖 GPU putback / 微优化 | GPU 饱和时没有端到端收益，应先减少 warp + decode 总工作量 |
| Warp TRT / LMDM FP16 作为默认 | 隔离变快但被 stitch 抵消或浏览器 fps 不变——不是无效，是本链与硬件下无额外用户侧收益 |
| 单卡硬塞大模型 | 见上一节：显存不是问题，主机内存与架构（无 FP8）才是 |

- 结论：**负结论也是结论**，它们划出"不要在这里继续投入"的边界

## Decisions

- **D1 素材不落仓库**：整理结果只在对话中提交审核；仓库只保留正文

- **D3 正文不写出处**：论文与仓库名可点名，但不写路径、日期与 commit
- **D4 边界**：稳与对归《工程改进》；市场归《行业全景》；原理归《介绍与技术路线》
- **D5 配图 3 张**：延迟链图、四类成本与加速方向图、硬件档位图（节点文本加双引号，放对应小节开头）
- **D6 标题规范**：不用桶标题、标题不用冒号、文内引用用 heading 链接
- **D7 搬迁规则**：迁出方（《工程改进》《数字人行业全景》）删除对应内容只留一句链接；两篇的 change 同步更新，避免两处重复

## Risks / Trade-offs

- [与《工程改进》的边界被写糊] → 本篇出现"稳定性 / 正确性"内容即视为越界；同理《工程改进》里不再保留速度结论

- [第一手数据缺失导致横评不够第一手] → 明确标"待补"，不用二手顶替
- [搬迁造成两篇读者断链] → 迁出方保留标题级链接，互链闭合
