# Design: docs-intern-intro（含待审核大纲）

## Context

- 伞 change 登记表 #1；统一写作骨架（为什么重要 → 现行做法 → 我们的工作 → 改进方向）。
- 目标读者：**自己**（回顾 + 后续推进素材 + 发文选题依据）。
- 定位：**数字人领域入门与路线总览**（教科书视角）；与《数字人行业全景》分工——后者写产业/产品/实测，本文写原理与流派。
- **核心框架（本次修正）**：数字人最重要的两个因素是 **动作（怎么动）** 与 **身份（长什么样、是不是同一个人）**。全篇围绕这两个因素组织：
  - **动作生成** 回答"怎么动"——模型直接预测什么
  - **身份呈现/渲染** 回答"身份靠什么落地"——画面怎么把身份保留并重演出来
  - 路线 = 动作生成方式与身份呈现后端的**具体搭配**；两者的搭配关系是本文要讲清的重点
- 正文目标路径：`management/docs/实习复盘/数字人介绍与技术路线.md`

## Goals / Non-Goals

**Goals：** 说清"数字人是什么、为什么重要、几条路线怎么做、优缺点、怎么评、我们为何这么选"。

### 三、`## 技术路线版图`
- 3.0 `> 框架说明`：**两个因素——动作与身份**
  - **动作**：怎么动（表情、口型、头姿、手势、身体）→ 由**动作生成**决定：模型直接预测什么
  - **身份**：长什么样、是不是同一个人（外观、纹理、几何）→ 由**身份呈现/渲染后端**决定：身份靠什么落地
  - 关键表述：**动作生成对应"怎么动"，身份呈现/渲染后端对应"身份怎么落地"**；两者的搭配受接口契约与身份资产成本约束，本文讲的就是这套搭配关系（见 3.3）
  - 源材料（《数字人基础》）用的说法是"生成方式 × 渲染资产后端"，本文把它精确化为"动作生成 × 身份呈现"，并显式写出搭配约束
- **完整路线清单**（依据 `digital-human-avatar-survey` 表 2 的六条 taxonomy + `数字人渲染器专题` §二的 renderer 光谱）：

| # | 路线 | 核心表示 | 代表工作 | 优势 / 限制 |
|---|------|---------|---------|------------|
| 1 | 2D talking-head / latent inpainting | landmarks、mask、latent | MuseTalk、SadTalker | 简单快、生态成熟 / 身体手势弱、3D 一致性弱 |
| 2 | 结构化动作策略 | SMPL-X、FLAME、MANO、VQ motion token | EMAGE、Audio2Photoreal、EMO2 | 可解释可控、动作可单独评估 / 仍需 renderer |
| 3 | 动作扩散 + 快速渲染器 | 低维 motion + warping GAN/renderer | ChatAnyone；**Ditto、Avatar Forcing（我们的主线）** | 实时性强、工程闭环清晰 / 画面自由度低于整帧大模型 |
| 4 | 视频基座模型适配 | video latent、DiT/MM-DiT、ReferenceNet、LoRA | OmniAvatar、HunyuanVideo-Avatar、wan-streamer | 全画幅表达强 / 训练推理重、资产不可复用 |
| 5 | **3D 资产驱动** | 3DGS 高斯 / NeRF 场 / **mesh + blendshape·FLAME rig** | 5a 学习式：GaussianTalker、UIKA、FlexAvatar；**5b 参数化装配式：FLAME/ARKit blendshape + 游戏引擎渲染（工业实时角色，Audio2Face 类）** | 身份可复用、渲染可控 / 注册难、训练成本高、极端动作风险 |
| 6 | 掩码局部多人控制 | face mask + localized cross-attention | HunyuanVideo-Avatar | 可指定说话人 / 依赖 mask |

- 注：**Blendshape/FLAME 作为动作表示的深度内容在《数字人动作》**，这里只作为资产接口与后端出现，一句话 + 链接，不展开
- **必须辨析（易读歪点）**：FLAME / blendshape / 隐式关键点 / latent 是**动作表示**，属于「动作空间生成」的内部表示形式，**不是第四种生成方式**；它们同时出现在身份呈现后端里，是因为同一套参数化表示两用——既是动作生成要预测的目标，又是身份资产的驱动接口（如 FLAME canonical space 驱动 3DGS）。两因素说明下必须有一句显式辨析；5b 行的核心表示写成「blendshape/FLAME 系数 → 驱动 rigged mesh」，避免读成"blendshape 是一条生成方式"
- 3.3 **动作生成与身份呈现的绑定关系**（本次修正的重点，必须写清）
  - 渲染器与其输入契约绑定：Ditto/LivePortrait renderer 吃 canonical keypoints；LIA-X 吃 40D motion code；FLOAT/Avatar Forcing decoder 吃 512D appearance + `r=Bα`
  - 身份资产有训练/注册成本：3DGS/NeRF 必须先把身份训练进资产，换身份 = 重新训练；FLAME/ARKit 走参数化接口，换身份成本低
  - 端到端整帧视频生成不换后端（身份就长在模型权重/LoRA 里）
  - **结论**：动作生成与身份呈现的搭配受接口契约与身份资产成本约束，**不是任意搭配**；换后端要付出的代价，取决于身份表示的可复用性
- 补充：**身份呈现后端视角**（`数字人渲染器专题` §二）——2D warping renderer（Ditto/LivePortrait、LIA-X、FLOAT/AF decoder）、FLAME/3DMM、NeRF/3DGS 专人资产、**ARKit/blendshape/game engine**、视频级后处理（Wav2Lip/LatentSync，非完整 renderer）；**这些后端解决的都是"身份怎么被保留并重演"**
- 论证/结论：路线分野在「中间表示 + 渲染后端」；同一任务可由多条路线完成；**「操控 3D 模型」（参数化/rigged + 引擎渲染）是独立且工业成熟的一条路线**，与 5a 学习式资产区分（5b 资产为手工/标准接口，5a 需训练）
- 素材：`digital-human-avatar-survey` 表 2、`数字人渲染器专题` §二/§三、`动作空间专题` 表示谱系

### 四、`## 数字人系统与实时性（现行做法）`
- 表达内容：级联四组件；三种架构（级联/端到端/混合，含 A2-LLM 535ms、级联 3.2s）；两条工程战线（传输层 WebRTC；推理层流式分块）+ 轻量技巧；Agent 能力
- 论证/结论：系统延迟由排队与分块决定，不是单纯模型速度
- 引用：链《CyberVerse框架》看落地形态

### 五、`## 评价体系`（原「评价口径」，扩写为独立章节）
- 5.1 `### 先立三个评价维度`
  - 表：**维度 | 问什么 | 包含什么 | 常见误读**
    - 表现质量：像不像、自然不自然 | 画质、身份一致性、音唇同步、动作自然度、时序稳定（闪烁/抖动） | 只看单帧画质，忽视长时漂移与闪烁
    - 表现范围：能驱动到哪里 | 只改嘴 / 头肩说话 / 上半身手势 / 全身 / 带背景与多人 | 把任务名当能力边界
    - 工程性能：能不能用起来 | 首帧延迟、持续帧率、显存与 GPU、并发 | 拿论文 FPS 当产品准入标准
  - 结论：评方案先分清在看哪一层；三个维度不能混着比，也不能互相代替；任务名（lip sync / talking head / 3D avatar）是说表现范围或实现形态，被当成能力边界是常见误读
- 5.2 `### 五个指标族`
  - 表（代表指标 + 回答什么问题）：唇同步（Sync-C/D）、身份与长时漂移（CSIM/CSIM-drift/LPIPS-drift）、画质（PSNR/SSIM/LPIPS/NR-IQA）、时序流畅（Dino-S/flow_smoothness）、效率（FPS/TTFF/延迟/显存）
- 5.3 `### 指标与维度的对应`
  - 顺带点明两个因素与指标的对应：**动作** → 唇同步、动作自然度；**身份** → CSIM 身份一致性、画质；两者共同影响时序稳定
  - 把五族映射回三维度：效率 → 工程性能；其余四族 → 表现质量的不同侧面（音唇 / 身份 / 画质 / 时序）
  - **指出缺口**：表现范围这一维度目前几乎没有通用量化指标，只能靠能力描述——这是评价体系自身的空白（我们的观察）
- 5.4 `### 两条提醒`
  - 论文 FPS ≠ 产品 SLA；身份度量（CSIM）有适用边界，风格化/长时/跨环境会失效
- 论证/结论：指标各有适用域；维度层比指标层更能指导选型
- 引用：链《数字人身份》看 CSIM 边界

### 六、`## 我们的选择与理由`
- 表达内容：调研时间线（06-08 启动 → 06-22 选型）；选型结论（GAGAvatar/UIKA 前馈式）；最终体系（CyberVerse + AvatarForcing/Ditto）
- 论证/结论：动作空间便于实时化与控制；前馈式 3D 建 avatar 成本低
- 引用：实测支撑链《数字人行业全景》
