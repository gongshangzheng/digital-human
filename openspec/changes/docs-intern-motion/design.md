## 【待审核】正文大纲（10 节 / 3 张图）

### 一、`## 为什么重要`

- 动作是数字人两个核心因素之一（另一是身份，见 [[实习复盘/数字人身份|数字人身份]]）；它决定**可看性**：动作不自然的数字人，画质再好也像"贴图在动"
- **动作是分层递进的能力**，每层门槛与代价不同：音唇同步（能不能对得上嘴）→ 表情与听态（像不像在说、听的时候有没有反应）→ 手部与全身（整段肢体是否协调）
- 边界一句话：本文只讲"怎么动"，不碰渲染、实时性与身份
- **配图 1**：`flowchart LR` 三层能力递进（音唇 → 表情与听态 → 手部与全身），每层标一个"门槛"与"代价"

### 二、`## 动作空间谱系`（**表示层的深度内容在本节**）

- 定调：动作空间生成要选一种**表示**当预测目标；表示决定了后面能怎么控制、能被谁复用
- **按"人能读懂多少"排一张谱系表**（本篇是唯一讲透的地方）：
  1. **3DMM 系数**（BFM / FLAME）：表情系数 + 头姿系数，每维有明确语义
  2. **Blendshape 系数**（ARKit 52 维等，工业标准接口）：可直接接引擎与直播软件
  3. **显式关键点与参数化模型这一族**（**要单独讲透**）：landmarks（68 点 iBUG 300-W / MediaPipe Face Mesh 468·478 / BlazeFace / 3D 关键点、3DMM 拟合）、**FLAME**（shape·expression·pose + LBS，输出 mesh 与 blendshape）、ARKit 标准接口；写清语义由人定义、可直接读写、但覆盖有限（纹理光影不在其中）、协议互不兼容
  4. **部署运动向量**（Ditto 265 维）：scale + pitch/yaw/roll + translation + expression，**不含关键点**（kp 由源侧回填）
  5. **隐式关键点**（LivePortrait 紧凑关键点、FOMM 类）：从数据里学出来，无标注语义
  6. **latent**：AF 的 20 维 α（对 renderer 的接口是 `r = Bα` 的 512 维，实际只有 20 个独立方向）
- **可控性从哪来**（本节的核心洞见，写成对照）：显式一族 → 直接读写某个点或系数；隐式表示 → 靠**扰动观察反推**局部映射（Ditto 的 21×3 位移表就是这么来的）；latent → 靠 probe 与解耦
- 训练来源对比（各表示从哪来：扫描建模 / 3DMM 拟合 / 无监督关键点 / 端到端学）
- **配图 2**：`flowchart LR` 谱系与可控性来源对照（六类表示 → 控制手段）
- 引用：intro 的表示谱系表（只给一行，深度在此）；《数字人身份》里同一批表示在身份侧的用法

### 三、`## 音唇同步`（第一层）

- 现行做法三层递进：**Wav2Lip 系局部替换**（只换嘴部区域，稳定便宜，动作范围受限）→ **MuseTalk 系 latent inpainting**（在 latent 空间重绘嘴部，画质与稳定性兼顾）→ **视频基座 / 端到端**（整帧生成，能带身体与场景，代价高）
- 判据与前置：**先确认时间对齐**（offset 问题）再看同步指标；两代口径 LSE-C / LSE-D（SyncNet 系）与 sync_c / sync_d（新口径）**不能横向排序**；StableSyncNet 作为冻结监督与诊断器的定位
- 训练期的手段：同步损失、LoRA 注入、音素辅助头（待验证）
- 结论：这一层是"能不能用"的门槛，也是最成熟的一层——我们的工作集中在把**中文音频**接进原模型（见第六节）
- 引用：《音画同步专题》

### 四、`## 表情与听态`（第二层）

- 表情侧：语义一致性（表情要跟内容走）、强度控制（我们遇到的"表情太用力"问题）
- 听态侧：双向对话里 listener 的反应——AF 用 **Dual Motion Encoder** 把"用户正在做什么"与"avatar 这次要怎么说"编码成同一种条件，因此能生成听态画面而不只是说话画面
- 结论：这一层决定"像不像在对话"，比音唇同步更容易被忽略，也更难评
- 素材：knowledge/《Avatar Forcing 模型精读》、《音画同步专题》边界节

### 五、`## 手部与全身动作`（第三层）

- 现行做法：co-speech gesture 生成（语音驱动手势），主流在"动作序列生成 + 身体渲染"两段式
- 我们**没做这一层**，写清原因与接入成本（渲染后端要换、动作数据要求高、实时性预算被吃掉）
- 结论：这是"我们做到哪层、市面到哪层"的差距所在，留到第九节展开

### 六、`## 中文音频适配（桥系列）`

- 问题：原模型吃英文音频特征，中文音频接不上
- 方案演进（三段，每段解决一个具体故障）：
  1. **蒸馏桥**：在中文 wav2vec2 与冻结主干之间放一个桥接层（Linear 9216→512 + LN + SiLU，4.7M 参数），主干保持冻结，避免有限中文数据冲掉原有能力
  2. **geom 桥**：蒸馏桥会把中文音节**压塌**（几何上不可分）→ 加**帧对单边 hinge 损失**，惩罚同帧特征被拉近
  3. **georkd**：再加 RKD 关系蒸馏，保持英文老师侧的成对距离结构
- **指标表**（必须带边界）：md_georkd_best 的 sync_c/sync_d 优于对照锚；**但多域设置同时改变了样本数量、来源域与身份多样性，人工判定未完成**——只能写"多域训练值得继续验证"，**不能写成"数据量不足已被证实"**
- 引用：第七节的微调形态（桥属于"全冻结 + 桥"这一档）

### 七、`## 微调方法与注入点`

- **微调形态谱系**（全冻结 + 桥 / LoRA / 单层解冻）与各自代价
- 几条实战结论（每条都要有实验背书才写）：
  - **注入点比 rank 更影响结果**
  - **全开放的代价**：桥与主干失去配合
  - **解冻单层的判据**：找历史空白区
  - **多域结果不能直接归因成"数据量是瓶颈"**
  - **不同口径的指标不能横向排序**
- 注入点审计方法（怎么确认某一层真的在被使用）
- 引用：《微调策略专题》与《音画同步专题》的同步损失部分

### 八、`## Ditto 的眼嘴拆分`（四层机制）

- 问题：同一段音频驱动下，怎么让眼睛和嘴巴各自受控
- **四层机制**（本文的核心技术叙事）：
  1. **表示层**：motion 来自 LivePortrait 风格的 Motion Extractor；exp 可按 **21×3 位移表**（63 维）操作，这些维度**没有预训练语义标签**，是靠逐维扰动观察后建立的**后验控制映射**
  2. **条件层**：音频（HuBERT）决定口型，**眼部状态**（眼睛开合比 + 瞳孔位置）单独提示眨眼与视线，参考 keypoints 适配这张脸的几何，emotion label 控制表情强度
  3. **训练层**：嘴、眼、头姿收敛速度不同，统一权重会让某个区域学不好 → 按区域分组、观察相邻轮次误差变化后动态调权
  4. **运行时**：用 alpha mask 逐区域混合"驱动值"与"参考帧原值"（唇部取驱动值、其余保留源值）
- 代码级证据（路径与索引只记 change，正文不写）：唇部控制索引、眼部索引、`motion_stitch` 中的掩码实现
- 结论：**可控性不是模型自带的，是表示层 + 条件层 + 训练层 + 运行时四层叠出来的**——这也解释了为什么"换个表示就要重做一遍控制"
- **配图 3**：`flowchart TB` 四层机制（表示 → 条件 → 训练 → 运行时）

### 九、`## 可能的改进方向`

- **我们做到哪层、市面到哪层**：我们覆盖音唇同步与表情/听态，手部与全身未接
- **听态质量**：听态目前是"有反应"，离"反应得体"还有距离；怎么评也是空白
- **表情强度控制**："太用力"问题的根因与可调手段
- **手部接入成本**：需要换渲染后端与数据，短期内不划算
- **表示与控制的可复用性**：能不能把"扰动观察反推控制"这套方法沉淀成流程（新表示接入时的固定动作）
