# 数字人介绍与技术路线

## 数字人是什么

【已验证】这件事要分两层看：

- **数字人（模型）**：给定驱动信号（音频/文本），生成可控形象的技术问题
- **数字人系统**：把 ASR、LLM、TTS、Avatar 渲染串成可对话产品的工程形态

一句话：**用可驱动的形象，把语音或文本变成会说话、有表情的画面。**

评任何一个方案，先问三个问题【已验证】——不要混在一起看：

| 问题 | 含义 |
|------|------|
| 表现质量 | 像不像、自然不自然（画质、身份、音唇、动作、闪烁） |
| 表现范围 | 只改嘴 / 头肩说话 / 上半身手势 / 全身 / 带背景 |
| 工程性能 | 首帧等多久、能否持续播放、显存与 GPU 是否够 |

文献里的任务名（换嘴配音 lip sync、talking head、3D avatar）描述的是表现范围或实现形态，**不能替代上面三问**，也不是路线划分依据。

## 为什么重要

- **产品价值**：把 AI 回复从文字、语音升级为可见的面对面交互，是对话式产品临场感最强的载体【待验证·判断】
- **落地形态**：会议面试官数字人（本项目方向）、虚拟客服、直播主播、陪伴 Agent【已验证】
- **技术价值**：数字人串起语音理解 → 语言生成 → 语音合成 → 视觉生成的完整多模态链路，是端到端系统的集成试炼场【待验证·判断】
- **关键约束**：实时性决定可用性。对话场景首帧延迟到秒级就会明显破坏自然感【已验证】

## 技术路线版图

### 先立框架：两条轴，不是互斥路线

【已验证】knowledge/《数字人基础》原文：

> "生成方式与渲染后端可自由组合，不能混成互斥路线。动作空间模型既可以配 2D renderer，也可以配 FLAME、NeRF 或 3DGS。"

| 轴 | 取值 |
|----|------|
| **生成方式**（模型直接预测什么） | ① 局部换嘴 / 视频级修正 ② 动作空间生成 ③ 整帧视频生成 |
| **渲染/资产后端**（画面靠什么落地） | ① 2D warping renderer ② FLAME/3DMM ③ NeRF/3DGS 专人资产 ④ ARKit/blendshape/game engine ⑤ 视频级后处理 |

《5分钟认识数字人》的说法更直白："3D 资产不是第四种互斥模型，而是画面如何落地的一种后端；可以和动作空间组合。"

### 六条常见路线

【已验证·`digital-human-avatar-survey` 表 2 的 taxonomy】：

| # | 路线 | 核心表示 | 代表工作 | 优势 | 限制 |
|---|------|---------|---------|------|------|
| 1 | 2D talking-head / latent inpainting | landmarks、mask、latent | MuseTalk、SadTalker | 简单快、生态成熟 | 身体手势弱、3D 一致性弱 |
| 2 | 结构化动作策略 | SMPL-X、FLAME、MANO、VQ motion token | EMAGE、Audio2Photoreal、EMO2 | 可解释可控、动作可单独评估 | 仍需 renderer |
| 3 | 动作扩散 + 快速渲染器 | 低维 motion + warping GAN/renderer | ChatAnyone；**Ditto、Avatar Forcing（我们的主线）** | 实时性强、工程闭环清晰 | 画面自由度低于整帧大模型 |
| 4 | 视频基座模型适配 | video latent、DiT/MM-DiT、ReferenceNet、LoRA | OmniAvatar、HunyuanVideo-Avatar | 全画幅表达强 | 训练推理重、资产不可复用 |
| 5a | 3D 资产（学习式） | Gaussian particles、NeRF field | GaussianTalker、UIKA、FlexAvatar | 身份可复用、渲染可控、几何一致 | 注册/训练成本高、极端动作风险 |
| 5b | **3D 资产（参数化装配式）** | **mesh + blendshape/FLAME rig（ARKit 52 等标准接口）** | FLAME/3DMM 系、Audio2Face 类（游戏引擎渲染） | 接口标准、可跨软件、实时可靠 | 写实度靠美术资产、制作成本高 |
| 6 | 掩码局部多人控制 | face mask + localized cross-attention | HunyuanVideo-Avatar | 可指定说话人 | 依赖 mask、复杂互动未解 |

**"操控 3D 模型"就是 5b**：先有可驱动的 3D 资产（网格 + 表情基/骨骼），音频回归出 blendshape/FLAME 系数，再由传统图形管线渲染。它与 5a 的区别是资产来源——5b 靠美术制作、接口标准化（ARKit 52 blendshape 等），5a 靠训练得到（3DGS/NeRF）。5b 在工业实时角色（虚拟主播、游戏 NPC、客服数字人）里最成熟；我们没实测过，故标【待验证】。

**路线可以组合**【已验证】：EMAGE 的 motion 可进 photoreal renderer；Audio2Photoreal 把 face/body/hand motion 接到 personalized renderer；One Shot, One Talk 把 2D diffusion 伪视频与 SMPL-X/3DGS-mesh 资产结合。

### 渲染后端光谱

【已验证·`数字人渲染器专题` §二】动作空间路线必须配 renderer，后端选择决定画质与可替换性：

| Renderer / 后端 | 输入契约 | 典型用途 | 替换难度 |
|---|---|---|---|
| Ditto / LivePortrait renderer | reference appearance、canonical keypoints、pose/exp/translation | one-shot 音频驱动头像 | 高（与 motion 表示强绑定） |
| LIA-X renderer | source identity/features + 40D motion code | T2AV motion 解码 | 高（与 flow-warp 绑定） |
| FLOAT / Avatar Forcing decoder | 512D appearance `s` + 512D motion 接口 `r=Bα` | Motion AE / 交互头像 | 高（与 20D α 和 Direction 基绑定） |
| FLAME / 3DMM renderer | mesh、表情/头姿系数、相机/光照 | 可解释控制、3D 资产驱动 | 中 |
| NeRF / 3DGS avatar | 专人可渲染资产 + motion/pose | 专人高质量数字人 | 高（需专人训练） |
| **ARKit / blendshape / game engine** | 标准 blendshape、rig、材质资产 | 工业实时角色 | 中（接口标准、写实度靠资产） |
| Wav2Lip / LatentSync | 视频帧 + 音频/同步条件 | 口型替换/视频级修正 | 低到中（后处理，非完整 renderer） |

一个具体数据点【已验证】：LIA-X decoder 在 A10、512²、bf16、batch=1 下约 **333ms/帧**——渲染器本身就可能是速度瓶颈，不只是生成模型。

### 动作表示谱系

【已验证·详见《数字人动作》】表示按「人能读懂多少」排列：

3DMM 系数（BFM/FLAME，语义高）→ **Blendshape 系数（ARKit 52 维，工业标准接口）** → 隐式关键点（LivePortrait，隐式 blendshape）→ latent（Ditto 265 维、Avatar Forcing 20 维）。

越靠后越贴模型内部、越难人工干预。Blendshape 的深度内容写在《数字人动作》，这里不展开。

## 数字人系统与实时性（现行做法）

【已验证】级联四组件：ASR → LLM → TTS → Avatar 渲染。三种架构：

| 架构 | 特点 | 数据 |
|------|------|------|
| 级联 | 组件独立、可控、延迟高 | 流式链路约 3.2s |
| 端到端 | 单模型吃完整链路 | A2-LLM TTFA 535ms |
| 混合 | 级联框架 + 端到端局部模块 | — |

延迟差距主要来自**分块等待与组件间排队**，不是单纯模型算得慢。

两条工程战线【已验证】：
- **传输层**：实时交互基本必选 WebRTC（自带 jitter buffer、NetEQ 丢包隐藏、抗弱网）；WebSocket 简单但平滑要自己做
- **推理层**：流式 TTS 分块 + Avatar 异步渲染，减少首帧等待；轻量技巧包括滑动窗口重叠融合（LiteAvatar 1 秒窗口）、静音回退中性口型、说话/静音状态机

系统之上通常还集成 Agent 能力（RAG 检索、工具调用、记忆人格）。具体落地形态见《CyberVerse框架》。

## 评价口径

【已验证】五大指标族：

| 指标族 | 代表指标 | 回答的问题 |
|--------|---------|-----------|
| 唇同步 | Sync-C / Sync-D | 嘴型与声音是否对得上 |
| 身份与长时漂移 | CSIM / CSIM-drift / LPIPS-drift | 是否还是同一个人、长时是否偏离 |
| 画质 | PSNR / SSIM / LPIPS / NR-IQA | 画面质量 |
| 时序流畅 | Dino-S / flow_smoothness | 相邻帧是否平滑、有无闪烁抖动 |
| 效率 | FPS / TTFF / 延迟 / 显存 | 能否实时、算力代价 |

两个关键提醒：
- **论文 FPS ≠ 产品 SLA**【已验证】：实验室吞吐与产品准入标准往往差一个数量级
- **身份度量有适用边界**【已验证】：CSIM 在风格化、长时、跨环境场景会失效，详见《数字人身份》

## 我们的选择与理由

【已验证】时间线：2026-06-08 启动三条路线调研（2D talking-head / 3D Gaussian Splatting 头像 / 扩散式生成），2026-06-22 得出结论——**以 GAGAvatar / UIKA 系前馈式方案为主要探索方向**。

最终落地的系统形态：**CyberVerse（实时数字人 Agent 框架）+ AvatarForcing / Ditto 模型插件** `@4968280`。

理由要点（实测支撑见《数字人行业全景》）：
- 我们选的主线属于**路线 3（动作扩散 + 快速渲染器）**：算力集中在运动生成上，便于实时与控制
- 3D 资产侧优先**前馈式（UIKA/GAGAvatar 系，属 5a）**：单图建 avatar 成本低，适合快速换形象

## 开放问题与改进方向

- **唇、头、手势统一框架缺位**：这是领域级空白【已验证·survey-map】
- **扩散路线实时化困难**：整帧扩散（路线 4）的实时化仍是主要瓶颈【已验证】
- **身份度量标准化**：CSIM 无统一协议、风格化失效【已验证】——见《数字人身份》
- **3D 资产的两条路各有硬门槛**：5a 前馈化的硬件门槛（MATCH 需多视角 + SM90）、5b 的美术制作成本【待验证】
- **多路线组合的工程化**：motion 与 renderer 的契约解耦（替换 renderer 不改 motion）仍是开放问题【待验证】
- 【待补】3DGS 各方法的 RTF / 显存实测、视频基座路线（路线 4）的延迟指标——评测框架数据在 CyberVerse，尚未复制到本仓库
