# 数字人介绍与技术路线

## 数字人是什么

这件事要分两层看：

- **数字人（模型）**：给定驱动信号（音频/文本），生成可控形象的技术问题
- **数字人系统**：把 ASR、LLM、TTS、Avatar 渲染串成可对话产品的工程形态

一句话：**用可驱动的形象，把语音或文本变成会说话、有表情的画面。**

数字人里最重要的两个因素是**动作**和**身份**：动作是"怎么动"（表情、口型、头姿、手势、身体），身份是"长什么样、是不是同一个人"（外观、纹理、几何）。看一个方案好不好，先看它把这两件事分别交给了谁。

## 为什么重要

- **产品价值**：把 AI 回复从文字、语音升级为可见的面对面交互，是对话式产品临场感最强的载体（我们的判断）
- **落地形态**：会议面试官数字人（本项目方向）、虚拟客服、直播主播、陪伴 Agent
- **技术价值**：数字人串起语音理解 → 语言生成 → 语音合成 → 视觉生成的完整多模态链路，是端到端系统的集成试炼场（我们的判断）
- **关键约束**：实时性决定可用性。对话场景首帧延迟到秒级就会明显破坏自然感

## 技术路线版图

### 先立框架：动作与身份两个因素

| 因素 | 回答的问题 | 由什么决定 | 取值 |
|------|-----------|-----------|------|
| **动作** | 怎么动（表情、口型、头姿、手势、身体） | **动作生成**——模型直接预测什么 | ① 局部换嘴 / 视频级修正 ② 动作空间生成 ③ 整帧视频生成 |
| **身份** | 长什么样、是不是同一个人（外观、纹理、几何） | **身份呈现 / 渲染后端**——身份靠什么落地 | ① 2D warping renderer ② FLAME/3DMM ③ NeRF/3DGS 专人资产 ④ ARKit/blendshape/game engine ⑤ 视频级后处理 |

两侧的取值不要混淆：**FLAME、blendshape、隐式关键点、latent 是"动作表示"，属于动作空间生成内部的不同表示形式，本身不是第四种生成方式**。它们同时在身份后端里出现，是因为同一套参数化表示两用——模型预测的系数既是动作生成的输出，又能直接当身份资产/渲染器的驱动接口。

路线按「动作生成 + 身份呈现」的搭配划分，而不是按文献里的任务名（换嘴配音 lip sync、talking head、3D avatar）划分——同一个任务名底下，可能用的是完全不同的搭配。

### 动作生成与身份呈现的搭配约束

两侧不是任意搭配，绑定关系来自三处：

- **渲染器与其输入契约绑定**：Ditto / LivePortrait renderer 吃 canonical keypoints，LIA-X 吃 40D motion code，FLOAT / Avatar Forcing decoder 吃 512D appearance 加 `r=Bα` 的 motion 接口。动作表示一换，渲染器通常要跟着换。
- **身份资产有训练/注册成本**：3DGS / NeRF 必须先把身份训练进资产，换身份等于重新训练；FLAME / ARKit 走参数化接口，换身份只是换一组系数或 rig，成本低。
- **端到端整帧视频生成没有可换的后端**：身份就长在模型权重或 LoRA 里。

所以换后端要付出的代价，取决于身份表示的可复用性。

### 六条常见路线

当前领域常用的分类如下：

| # | 路线 | 动作生成（怎么动） | 身份呈现（怎么落地） | 代表工作 | 优势 / 限制 |
|---|------|------------------|--------------------|---------|------------|
| 1 | 2D talking-head / latent inpainting | 局部换嘴、视频级修正（landmarks / mask 驱动 latent inpainting） | 参考图或视频（2D warping，身份就是参考外观） | MuseTalk、SadTalker | 简单快、生态成熟 / 身体手势弱、3D 一致性弱 |
| 2 | 结构化动作策略 | 动作空间生成（SMPL-X、FLAME、MANO、VQ motion token） | 参数化渲染器（FLAME / 3DMM / SMPL-X） | EMAGE、Audio2Photoreal、EMO2 | 可解释可控、动作可单独评估 / 仍需 renderer |
| 3 | 动作扩散 + 快速渲染器 | 动作空间生成（低维 motion，扩散生成） | warping GAN 或 renderer（Ditto、LivePortrait、LIA-X、FLOAT/AF decoder） | ChatAnyone；**Ditto、Avatar Forcing（我们的主线）** | 实时性强、工程闭环清晰 / 画面自由度低于整帧大模型 |
| 4 | 视频基座模型适配 | 整帧视频生成（video latent、DiT/MM-DiT） | 身份靠参考图条件注入（ReferenceNet、LoRA）——动作与身份一起生成 | OmniAvatar、HunyuanVideo-Avatar | 全画幅表达强 / 训练推理重、资产不可复用 |
| 5a | 3D 资产（学习式） | 动作空间生成（motion、pose） | 3DGS 高斯、NeRF 场（身份需先训练进资产） | GaussianTalker、UIKA、FlexAvatar | 身份可复用、渲染可控、几何一致 / 注册训练成本高、极端动作风险 |
| 5b | **3D 资产（参数化装配式）** | 动作空间生成（**blendshape / FLAME 系数**） | **rigged mesh 美术资产 + 游戏引擎渲染**（ARKit 52 等标准接口） | FLAME/3DMM 系、Audio2Face 类 | 接口标准、可跨软件、实时可靠 / 写实度靠美术资产、制作成本高 |
| 6 | 掩码局部多人控制 | 整帧视频生成 + 局部控制（face mask、localized cross-attention） | 参考图条件 + 掩码限定说话人 | HunyuanVideo-Avatar | 可指定说话人 / 依赖 mask、复杂互动未解 |

**"操控 3D 模型"就是 5b**：先有可驱动的 3D 资产（网格 + 表情基/骨骼），音频回归出 blendshape/FLAME 系数，再由传统图形管线渲染。它与 5a 的区别是资产来源——5b 靠美术制作、接口标准化（ARKit 52 blendshape 等），5a 靠训练得到（3DGS/NeRF）。5b 在工业实时角色（虚拟主播、游戏 NPC、客服数字人）里最成熟；我们没实测过。

**不同路线的分界就在两侧怎么配**：EMAGE 的 motion 可进 photoreal renderer；Audio2Photoreal 把 face/body/hand motion 接到 personalized renderer；One Shot, One Talk 把 2D diffusion 伪视频与 SMPL-X/3DGS-mesh 资产结合。

### 动作表示谱系

动作空间生成要选一种「表示」当预测目标——就是定下模型输出的那组数字，用什么样的格式来表示「怎么动」。按**人能不能读懂每一项**从高到低排：

| 表示 | 形式与维度 | 语义可读性 | 代表工作 |
|------|-----------|-----------|---------|
| **3DMM 系数**（BFM/FLAME） | 表情系数 + 头姿系数 | 高：每一维含义明确（下颌开合、眼球转动…） | SadTalker、FLAP |
| **Blendshape 系数** | ARKit 52 维等标准接口 | 高：工业标准，可直接接引擎 | LiteAvatar（32 维口型） |
| **部署运动向量** | 标度 + 三轴旋转 + 平移 + 表情（Ditto 265 维） | 中：可逐维扰动建立局部控制映射 | Ditto |
| **隐式关键点** | LivePortrait 紧凑关键点 | 低：名为 implicit blendshape，维度无天然语义 | LivePortrait |
| **整体面部 latent** | 512 维向量 | 低：容量大，但不能直接编辑 | VASA-1、FLOAT |
| **资产接口** | SMPL-X / ARKit / BVH / motion token | 高：跨软件通用，能直接驱动 3D 资产 | 3D avatar 生态 |

谱系两端的取舍：**显式端**可解释、可逐维编辑、能直接接游戏引擎与直播软件的工业管线；**隐式端**容量大、表达上限高，但想改一个「眼神」，得先做实验找出该动哪个维度。

三件值得记住的事实：

- **FLAME 系数语义清晰**：头部旋转、眼睛、下颌、眼睑、表情 blendshape 都能单独读写，所以能直接当可控条件塞进扩散模型（FLAP 就是这么做的）
- **FLAME 顶点自带 blendshape 与 LBS 蒙皮权重**：Gaussian avatar 若重建在 FLAME canonical space，每个 Gaussian 会继承对应顶点的形变权重，于是 FLAME 系数可以直接驱动 3DGS
- **隐式表示也能长出可控性**：LivePortrait 的经验是，紧凑隐式关键点虽没有 3DMM 那样的显式语义维度，但小型 MLP 能学出「眼睛再开一点」「嘴巴闭上一点」这类局部形变——Ditto 正是借这个机制实现 gaze / emotion / pose 的细粒度控制

表示的深度展开（含 Ditto 把眼部和嘴部拆开的四层机制）写在《数字人动作》，这里只给谱系。

### 渲染后端谱系

动作空间路线必须配 renderer；下面的后端决定**身份**怎么落地，也决定可替换性：

| Renderer / 后端 | 输入契约 | 典型用途 | 替换难度 |
|---|---|---|---|
| Ditto / LivePortrait renderer | reference appearance、canonical keypoints、pose/exp/translation | one-shot 音频驱动头像 | 高（与 motion 表示强绑定） |
| LIA-X renderer | source identity/features + 40D motion code | T2AV motion 解码 | 高（与 flow-warp 绑定） |
| FLOAT / Avatar Forcing decoder | 512D appearance `s` + 512D motion 接口 `r=Bα` | Motion AE / 交互头像 | 高（与 20D α 和 Direction 基绑定） |
| FLAME / 3DMM renderer | mesh、表情/头姿系数、相机/光照 | 可解释控制、3D 资产驱动 | 中 |
| NeRF / 3DGS avatar | 专人可渲染资产 + motion/pose | 专人高质量数字人 | 高（需专人训练） |
| **ARKit / blendshape / game engine** | 标准 blendshape、rig、材质资产 | 工业实时角色 | 中（接口标准、写实度靠资产） |
| Wav2Lip / LatentSync | 视频帧 + 音频/同步条件 | 口型替换/视频级修正 | 低到中（后处理，非完整 renderer） |

一个具体数据点：LIA-X decoder 在 A10、512²、bf16、batch=1 下约 **333ms/帧**——渲染器本身就可能是速度瓶颈，不只是生成模型。

## 评价体系

数字人的评价分两层，先把两个名词分清：

- **评价维度**：从哪个层面评——决定哪类事情要算进评价，是一组评价的骨架
- **评价指标**：用哪个数字量评——决定这个层面拿什么数字去比，是可测量的量

### 三个评价维度

数字人的评价维度有三个，每个回答一类问题：

| 评价维度 | 回答的问题 | 覆盖内容 | 常见误读 |
|---------|-----------|---------|---------|
| **表现质量** | 像不像、自然不自然 | 画质、身份一致性、音唇同步、动作自然度、时序稳定（闪烁与抖动） | 只看单帧画质，忽视长时漂移与闪烁 |
| **表现范围** | 能驱动到哪里 | 只改嘴 / 头肩说话 / 上半身手势 / 全身 / 带背景与多人 | 把任务名（talking head、lip sync）当成能力边界 |
| **工程性能** | 能不能用起来 | 首帧延迟、持续播放帧率、显存与 GPU 占用、并发路数 | 拿论文 FPS 当产品准入标准 |

三个评价维度不能混着比，也不能互相代替：画质最好的模型可能根本跑不到实时，实时性最好的模型可能只能动嘴。

文献里的任务名（换嘴配音 lip sync、talking head、3D avatar）说的是**表现范围或实现形态**，不是评价维度——把它们当成能力边界，是选型时最常见的一类误读。

### 五个指标族

每个评价维度下面通常有一组可量化的评价指标，当前常用五族：

| 评价指标族 | 代表指标 | 回答的问题 |
|-----------|---------|-----------|
| 唇同步 | Sync-C / Sync-D | 嘴型与声音是否对得上 |
| 身份与长时漂移 | CSIM / CSIM-drift / LPIPS-drift | 是否还是同一个人、长时是否偏离 |
| 画质 | PSNR / SSIM / LPIPS / NR-IQA | 画面质量 |
| 时序流畅 | Dino-S / flow_smoothness | 相邻帧是否平滑、有无闪烁抖动 |
| 效率 | FPS / TTFF / 延迟 / 显存 | 能否实时、算力代价 |

### 评价维度与评价指标的对应

把上面两节对齐——左列是三个评价维度，右列是它对应的评价指标族：

| 评价维度 | 对应评价指标族 | 量化程度 |
|---------|--------------|---------|
| **表现质量** | 唇同步、身份与长时漂移、画质、时序流畅 | 充分：四族量的是质量的四个侧面（音唇 / 身份 / 画质 / 时序），各有通用指标 |
| **工程性能** | 效率（FPS / TTFF / 延迟 / 显存） | 充分 |
| **表现范围** | **无** | **没有通用量化指标**，实践中只能定性描述能否驱动手、能否全身、能否多人 |

这层对应关系有三点要注意：

- **评价维度可以有空缺**：「表现范围」是三个维度里唯一没有被指标体系覆盖的一个——没有类似 CSIM、Sync-C 那样的通用度量，这是评价体系自身的空白
- **一个指标可以跨维度**：时序流畅同时受动作与身份影响，不专属某一侧
- **维度层更接近选型决策**：先确定要哪几个维度同时达标，再去看各维度的具体数字

换成动作与身份两个因素的视角：**动作**的质量主要由唇同步与动作自然度衡量，**身份**的质量主要由 CSIM 与画质衡量。

## 开放问题与改进方向

- **唇、头、手势统一框架缺位**：这是领域级空白
- **扩散路线实时化困难**：整帧扩散（路线 4）的实时化仍是主要瓶颈
- **身份度量标准化**：CSIM 无统一协议、风格化失效——见《数字人身份》
- **多路线组合的工程化**：motion 与 renderer 的契约解耦（替换 renderer 不改 motion）仍是开放问题
- 尚无实测数据：视频基座路线（路线 4）的延迟指标——评测框架数据在 CyberVerse，尚未复制到本仓库
