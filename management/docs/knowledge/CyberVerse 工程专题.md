## 一、先看实时链路的瓶颈在哪里

这轮排查关注的是服务器把数字人音视频发布给浏览器的链路。浏览器端以约 25 fps 消费；在隔离基准下，GPU 侧 decode、warp、LMDM、stitch 合计约 38.5ms/帧，而 25 fps 的时间预算只有 40ms。也就是说，GPU 已接近满载，生产环境中一点排队就会变成卡顿。

| 阶段（隔离口径） | 典型耗时 | 说明 |
|------------------|----------|------|
| decode | 17.7ms/帧 | fp16 engine |
| warp | 14.9ms/帧 | PyTorch autocast |
| LMDM | 3.9ms/0.4s block | 不是主要瓶颈 |
| stitch | 约 1ms | 不是主要瓶颈 |
| GPU 合计 | 约 38.5ms/帧 | 占 25 fps 的 40ms 预算约 96% |

这个基线改变了排查方向：不能把每次变慢都归到某个模型“算慢了”，很多生产侧抖动其实是 GPU 排队。

## 二、音频缺口：从发布节奏定位到 H.264 段尾等待

### 2.1 现象和证据

浏览器端出现周期性音频缺口。trace 显示 `SendAVSegment` 阶段存在 203–214ms 的背压，而每段时长也是 200ms：只要持续稍慢，浏览器的 jitter buffer 就会被耗尽，NetEQ 开始 concealment（用算法遮掩缺失音频），听感上就是呲呲声。

定位到 persistent H.264 流编码器后，发现解析器会持留段尾帧；旧 `encodeSegment` 在 `shortfall<=2` 时固定等待 200ms grace。真实 NVENC 编码约 15ms，但加上这段等待后变成约 215ms，恰好超过一段的预算。

### 2.2 修复和两阶段验收

第一步把 `shortfall==1` 视为解析器的确定性持留，立即返回，并由 deficit 在下一段记账偿还；只有 `shortfall==2` 仍保留 grace 兜底。

| 指标 | 修复前 | shortfall 修复后 |
|------|--------|------------------|
| 说话窗 cadence | 1.056–1.070 | 1.018–1.020 |
| send 段平均耗时 | 203–214ms | 194–204ms |
| concealment | 2.5–3.6% | 0.022% |
| 浏览器 fps | 23.5 / min 22.6 | 24.5 / min 24.4 |

第二步把 `publishAVSegment` 从“每段相对锚定”改成绝对播放锚点：deadline = 播放锚点 + 已发布内容的累计时长。这样单段超时不会逐段累加。240 秒会话中，稳态 cadence 达到 1.000；冷启动瞬态会有偏移，但下一窗口会自动回正，不再累积。

## 三、僵尸会话：会话能回收，不等于显存完全归零

浏览器被强杀后，原先 terminal 路径可能不删 session，导致会话长期不退出。修复采用三层兜底：terminal 路径补 `sessionMgr.Delete`、idle 驱逐触发清理、peer 侧 30 秒连接看门狗。

复现结果：kill 后约 29–31 秒进入 terminal，约 35 秒 session 归零，avatar backend 在 3 分钟 idle 后卸载。模型本体显存会释放，但排查同时发现 AvatarForcing 插件每个 load/unload 周期仍残留约 1.4GB 活跃分配；这是独立的插件泄漏问题，尚未在本 change 内修复。因此不能把结果写成“GPU 归零”。

## 四、性能优化：哪些有效，哪些没有端到端收益

| 尝试 | 局部结果 | 端到端结论 |
|------|----------|------------|
| decode fp32 → fp16 | 隔离口径 73.5→17.7ms/帧（4.2×） | 可证明 decode 侧显著变快 |
| warp fp16 TRT 引擎 | 隔离口径 14.9→11.8ms/帧（约 -21%） | 生产中 stitch 开销抵消，浏览器 fps 无明显变化，未采纳 |
| LMDM fp16 / DDIM 少步 | RTF 尾部约改善 5–8% | 浏览器 fps 基本不变，GPU 仍受 warp+decode 饱和限制，未单独作为默认方案 |
| CUDA stream 重叠 | 已有 warp/decode 双流 | GPU 90%+ 时两个 kernel 争同一组 SM，继续调优收益有限 |

这里的教训是：局部阶段变快不等于用户侧变快。每次优化都需要同时看阶段耗时、GPU 利用率、浏览器 fps、stall 和 TTFF，而不能只报一个 p95。

## 五、明确未采纳的方案

| 尝试 | 为什么不采纳 |
|------|--------------|
| 仅把 `ditto.fps` 从 25 改成 20 | online 因果窗口和 audio2motion→warp 时序以 25 fps 为前提；纯配置降帧导致帧数/音频对应错位，实测 fps 18.8、min 14.4、stalls 3 |
| 持续深挖 GPU putback / 微优化 | 在 GPU 饱和时没有端到端收益；应先减少 warp+decode 总工作量 |
| 把插件显存残留当作 zombie 已解决 | 会话回收与插件泄漏是两件事；后者每周期约残留 1.4GB，需单独立项 |

## 面试追问预案

**Q：为什么音频缺口看起来像网络问题，最后却是编码器等待？**

症状发生在浏览器端，但 trace 显示发布端 `SendAVSegment` 已经超过了 200ms 段预算。只看网络或只看模型推理都找不到这个固定等待。把发布时长、cadence 和 concealment 放到同一条时间线上后，才定位到 H.264 解析器持留段尾帧与 grace 等待的组合。跨端问题要先建立能串起来的观测，而不是按症状猜模块。

**Q：为什么绝对锚点比相对锚点更稳定？**

相对锚点让下一段从上一段结束时刻继续算，单段多出的几毫秒会成为下一段的基准，误差会累积。绝对锚点始终对齐到同一个播放时间轴，单段慢了只影响该段，后面可以回正。它并不会消除 GPU 算力不足，但能避免调度误差进一步放大。

**Q：为什么把 fps 从 25 降到 20 反而更差？**

这不是单纯的“少生成几帧”。Ditto 的 online 窗口、chunk 时长和 audio2motion→warp 的帧数对应都隐含 25 fps。只改一个配置会撕裂这些时序假设，导致音频和运动不再对齐。要降帧，需要同时重调窗口，必要时重训模型，而不是只改一个数字。
