## 先记一句话

实时数字人不是“模型每秒能算多少帧”这么简单，而是从音频输入到浏览器播放的一整条链，最慢的一段会决定用户是否感觉卡。

```mermaid
flowchart LR
    A[音频输入] --> B[音频特征]
    B --> C[动作生成]
    C --> D[Warp / Decoder]
    D --> E[编码与发布]
    E --> F[浏览器缓冲与播放]
    G[GPU争用/网络/会话] -.影响.-> C
    G -.影响.-> E
```

## 四个最常见的实时指标

| 指标 | 白话解释 | 只看它够不够 |
|---|---|---|
| **RTF** | 生成1秒内容要花几秒；小于1才有机会持续实时 | 不够，平均值会掩盖抖动 |
| **FPS** | 每秒实际产出或播放多少帧 | 不够，不说明首帧和卡顿 |
| **TTFF** | 用户等到第一帧的时间 | 不够，不说明后续能否持续 |
| **stalls** | 浏览器是否出现卡顿窗口 | 直接接近用户体验，但要结合原因分析 |

以 Ditto/CyberVerse 的生产链为例，最终可达到 RTF 约1、约25fps、stalls=0；这是 Decoder加速、GPU数据流、发布节奏与会话治理叠加的结果，不是单一模块的功劳。

## 为什么“模块变快”仍可能没用

假设 Warp 从30ms降到25ms，看上去快了。但如果后面的 Stitch 从2ms升到9ms，整个浏览器 FPS 可能完全不变。瓶颈只是从 Warp 移到了 Stitch 或 GPU 争用。

因此性能优化必须沿着完整链路看：

```text
阶段耗时
  → GPU是否排队
  → RTF平均与尾部
  → 发布节奏 cadence
  → 浏览器 FPS / stalls / TTFF
```

只报“某个 kernel 快了20%”不等于系统已经实时。

## 为什么发布节奏也会让音频出问题

即使模型算得够快，编码器或发布器每段多等一点时间，误差也会积累。浏览器提前缓存的音频被慢慢吃光后，会用算法遮掩缺口，用户听到的就是呲呲声或爆破音。

CyberVerse 的经验是：修模型不够，还要修段尾等待、绝对播放锚点、编码器复用和会话回收。实时是模型、系统和浏览器一起达标。

## 三条常见误解

1. **“RTF<1 就肯定流畅。”**
   平均 RTF<1 仍可能有长尾卡顿、首帧慢或发布节奏不稳。

2. **“GPU利用率高说明优化成功。”**
   高利用率也可能意味着已经饱和，新的并行或微优化只会让模块互相抢资源。

3. **“把25fps降到20fps一定更快。”**
   如果音频窗口、motion、warp和发布时序按25fps设计，只改一个配置会破坏对齐，反而更卡。
